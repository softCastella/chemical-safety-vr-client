# PPE 훈련 데이터·대시보드 후속 회의록

- 일자: 2026-08-26
- 범위: Unity 훈련 계측, 로컬 Express 서버, JSONL 저장, 실데이터 대시보드
- 상세 데이터 계약 기준: [PPE 훈련 대시보드 개념 및 측정 기준](./2026-08-21_PPE_Training_Dashboard_Concept.md)

## 1. 회의 목적

오늘까지 연결한 Unity 훈련 데이터와 대시보드의 실제 검증 결과를 정리하고, 담당 선생님의 피드백인 “현재 화면은 DB 값을 그대로 보여 준 느낌이며, 이 데이터를 어디에 사용할 수 있는지가 표현되어야 한다”를 후속 설계 기준으로 확정한다.

이번 후속조치의 핵심은 데이터 항목을 더 많이 나열하는 것이 아니다. 각 데이터가 어떤 문제를 발견하고, 관리자가 무엇을 판단하며, 콘텐츠·상호작용·운영을 어떻게 개선하는지 연결하는 것이다.

## 2. 오늘까지 완료한 작업

### Unity 실데이터 계측

- 한 플레이 회차를 `sessionId`로 묶어 JSONL에 저장한다.
- Meta 앱 범위 사용자 ID와 연령 범주 상태를 세션에 연결한다.
- 교육·훈련·테스트 모드와 시나리오, 과정 단계 변화를 기록한다.
- PPE 검사 시작·종료, 장비 종류, 청결·오염 상태, 선택 승인·거부를 기록한다.
- 시나리오별 필수 PPE와 미착용 목록 변화를 기록한다.
- 음성 클립 길이, 실제 재생시간, 완료·교체·중단 상태를 기록한다.
- PPE 구역의 실제 Controller Grip 입력을 음성 Trigger와 분리해 기록한다.
- Grip 시도와 결과를 `attemptId`로 연결하고 손, 입력 경로, hover PPE, 처리시간을 저장한다.

### 로컬 서버 연결

- Unity가 `POST /api/training-registrations`로 세션과 Meta 사용자 정보를 전송한다.
- 서버가 JSONL에 저장한 값을 `GET /api/training-registrations/:sessionId`로 다시 반환한다.
- Unity는 POST 성공만으로 완료 처리하지 않고, 다시 읽은 `sessionId`와 Meta 사용자 ID가 일치할 때 `가입이 완료되었습니다.`를 출력한다.
- 실제 세션 2건과 교사 왕복 시험 1건의 `serverReceivedAt`이 로컬 서버 기록에 남아 있다.

### 실데이터 대시보드

- 기존 모의 사용자·모의 세션·근거 없는 경고 수치를 제거했다.
- `Meta 사용자 ID → sessionId → 모드·시나리오 → 단계 → PPE·음성·Grab → 원본 이벤트` 관계로 조회한다.
- 사용자별, 시나리오별, PPE별, 단계별 데이터를 같은 세션 원본으로 연결한다.
- 검토 신호와 표의 행을 누르면 관련 원본 이벤트로 이동한다.
- JSON 파싱 오류가 발생하면 파일명, 행 번호, 파서 메시지, 깨진 원본 행을 표시한다.
- 폴더의 HTML을 `file://`로 직접 열어 API 호출이 실패하는 문제를 확인했다. 앞으로는 자동으로 `http://127.0.0.1:3000/dashboard/`로 이동한다.

### 실제 검증 결과

- 실제 세션: 8건
- 유효 이벤트: 828건
- JSON 파싱 오류: 0건
- 식별된 Meta 사용자: 1명
- 미식별 세션: 2건
- `flowState=Completed` 관찰 세션: 1건
- 완료 전 종료 세션: 7건. 종료 이유는 아직 확정하지 않음
- 최신 OpenXR 세션의 Grip 시도: 4회
  - `selected`: 2회
  - `no_ppe_hover`: 2회
- 관련 서버 자동 테스트 12건과 대시보드 JavaScript 구문 검사를 통과했다.

## 3. 담당 선생님 피드백

### 피드백 요지

현재 대시보드는 DB 또는 원본 로그에 저장된 항목을 화면에 그대로 출력한 인상이 강하다. 데이터가 존재한다는 사실만 보여 주지 말고, 이 데이터를 교육 관리·콘텐츠 개선·사용성 점검·운영 검증 중 어디에 활용할 수 있는지를 화면에서 이해할 수 있어야 한다.

### 피드백에 따른 판단

원본 데이터 표는 증거 확인을 위해 필요하지만 대시보드의 첫 화면이 되어서는 안 된다. 첫 화면은 다음 질문에 답해야 한다.

1. 지금 무엇을 먼저 확인해야 하는가?
2. 어느 사용자·모드·시나리오·단계·PPE에서 문제가 발생했는가?
3. 그 판단의 근거가 되는 원본 이벤트는 무엇인가?
4. 확인 결과 어떤 수정이나 운영 조치를 할 수 있는가?

대시보드는 `데이터 → 의미 → 조치 → 원본 근거` 순서로 읽혀야 한다.

## 4. 데이터 활용 관계

| 데이터 원본 | 알 수 있는 내용 | 활용 목적 | 가능한 후속조치 |
|---|---|---|---|
| 단계 전환 시각 | 특정 단계의 체류시간과 마지막 도달 단계 | 과정 병목 확인 | 안내 순서, UI 위치, 단계 난이도 수정 |
| Grip 시도·결과·hover PPE | 잡기 성공, 빈 공간 Grip, hover 후 Select 실패 | PPE 상호작용 사용성 점검 | Marker, Collider, Interaction Layer, Grab 범위 점검 |
| PPE 검사시간 | 장비별 확인에 걸린 시간 | 식별하기 어려운 PPE 확인 | 모델 대비, 결함 표현, 패널 설명 개선 |
| 청결·오염과 선택 결과 | 오염 장비 거부 및 정상 장비 선택 여부 | 안전 판단 이해도 확인 | 오염 시각물, 피드백 음성, 교육 문구 개선 |
| 필수 PPE 누락 목록 | 시나리오별 미착용 장비와 진행 변화 | 필수 장비 이해 및 착용 진행 확인 | 필수 목록 안내, 체크리스트, 착용 순서 개선 |
| 음성 길이·실제 재생시간 | 끝까지 들은 음성과 중간에 교체·중단된 음성 | 음성 안내 부담 확인 | 긴 음성 분할, 반복·순서·재생 조건 수정 |
| 사용자 ID·세션·모드·시나리오 | 같은 사용자의 반복 수행과 모드별 변화 | 교육 효과와 재수행 변화 확인 | 개인별 보충 교육, 모드 구성 비교 |
| 과정 완료·종료 직전 상태 | 완료 여부와 종료 직전 단계 | 이탈 구간 확인 | EXIT Point·종료 버튼 구분 계측 후 단계별 이탈 개선 |
| 서버 수신 시각 | Unity 전송과 서버 저장의 연결 여부 | 수집 파이프라인 운영 점검 | 전송 실패, 재시도, 네트워크·Endpoint 점검 |
| JSON 파싱 오류 원문 | 저장 형식이 깨진 파일과 행 | 데이터 무결성 점검 | 직렬화 문자 정제, 손상 레코드 수정 |

## 5. 대시보드 후속 설계 원칙

### 첫 화면

- 단순 이벤트 건수보다 `확인 필요 항목`을 먼저 보여 준다.
- 각 항목에 문제의 의미와 관리 목적을 한 줄로 설명한다.
- 경고 수치를 누르면 해당 사용자·세션·단계·PPE와 원본 이벤트로 이동한다.
- 정상 기록도 함께 표시해 문제 기록과 비교할 수 있게 한다.

### 상세 화면

- 사용자 상세에서는 모드, 시나리오, 단계, PPE, 완료시간, 반복 수행 변화를 한 흐름으로 보여 준다.
- 시나리오 상세에서는 필수 PPE 전체 목록과 실제 착용·누락·오염 선택 결과를 연결한다.
- PPE 상세에서는 검사시간, Grip 시도, 성공·실패, 선택 결과, 실제 착용 완료를 구분한다.
- 사용성 화면에서는 문제 수치뿐 아니라 해당 문제를 어떤 UI·Collider·음성·상호작용 수정에 활용할 수 있는지 표시한다.

### 지표 표시 조건

모든 지표에는 다음 네 요소가 있어야 한다.

1. 지표 정의와 계산식
2. 사용한 원본 이벤트
3. 계측된 세션 범위와 미계측 세션 구분
4. 해당 값으로 판단하거나 수정할 수 있는 대상

원본 이벤트가 없거나 경로가 구분되지 않은 값은 `0`이나 추정 원인으로 표시하지 않고 `미계측` 또는 `원인 미확인`으로 표시한다.

## 6. 후속조치

### 1순위: 현재 데이터로 바로 표현 가능한 활용

- 단계별 병목과 마지막 도달 단계에 `과정 개선용` 설명 추가
- PPE별 검사시간·선택 결과·Grab 결과에 `상호작용 및 장비 표현 개선용` 설명 추가
- 음성 완료·교체·중단에 `음성 길이·순서 개선용` 설명 추가
- JSON 파싱 오류와 서버 수신 여부에 `데이터 수집 안정성 점검용` 설명 추가
- 각 활용 카드에서 관련 세션과 원본 이벤트로 이동

### 2순위: 이미 저장된 데이터의 추가 연결

- Unity 세션 JSONL과 서버 등록 JSONL을 `sessionId`로 결합해 서버 수신 여부 표시
- `scene_loaded`를 이용해 앱 시작부터 PPE 룸 진입까지의 구간별 시간 표시
- `required_ppe_status_changed`를 이용해 필수 PPE 누락 개수의 변화 표시
- Meta 진단 상태와 미식별 세션을 연결해 계정 수집 성공 여부 표시

### 3순위: Unity 추가 계측 후 표현

- 선택 승인과 실제 착용 완료를 구분하는 `ppe_equipped`
- 전체 14종 PPE와 시나리오별 필수 목록의 세션 시작 스냅숏
- EXIT Point, 종료 버튼, 앱 생명주기를 구분하는 종료 경로 이벤트
- 태블릿 시작·완료, 퀴즈 문항별 선택·정답·최종 점수
- 텔레포트 시작·취소·도착과 Trigger 음성 스킵
- PPE hover 시작·종료 및 `hover → Grip → Select` 구간 시간
- 앱 버전, Android version code, 실행 플랫폼, 장치·XR runtime

추가 계측은 실제 Unity Play/Quest JSONL 검증 전까지 대시보드에 측정 완료로 표시하지 않는다.

## 7. 근본 원인과 영향 범위

### 근본 원인

초기 대시보드는 어떤 값을 저장할 수 있는지 확인하는 데 집중해, 값이 관리자의 판단과 개선 행동으로 어떻게 이어지는지 설명하지 못했다. 원본 데이터와 요약 수치의 연결은 확보했지만, 요약 수치가 필요한 이유와 실제 활용 맥락이 화면에 부족했다.

### 영향 범위

- 대시보드 정보구조와 설명 문구
- 집계 API의 세션·서버 수신 데이터 결합
- Unity의 추가 텔레메트리 이벤트 계약
- 운영자용 문제 확인 및 원본 증거 이동 흐름

Unity의 기존 교육 흐름, PPE Grab, UI, 음성 재생 동작은 이번 회의록 작성으로 변경하지 않는다.

## 8. 완료한 검증과 남은 검증

### 완료한 검증

- Unity JSONL 8세션·828이벤트·파싱 오류 0건 확인
- OpenXR Controller Grip 시도와 결과의 `attemptId` 연결 확인
- Unity → 로컬 서버 POST → JSONL 저장 → GET 재조회 확인
- 실데이터 API와 대시보드 조회 확인
- 사용자·시나리오·PPE·단계·원본 이벤트 연결 확인
- 폴더 직접 열기 실패 원인 확인 및 서버 URL 자동 이동 코드·테스트 추가

### 남은 검증

- 선생님 피드백을 반영한 `데이터 활용 목적` 중심 화면 재구성
- 서버 수신 정보와 Unity 세션의 대시보드 결합
- 추가 이벤트 계측 후 Unity Play·Quest 독립 실행 검증
- 운영 DB·인증·HTTPS 적용 뒤 Meta Horizon 배포 환경에서 원격 수집 검증

## 9. 최종 결정

대시보드는 DB 뷰어가 아니라 교육과 시스템을 개선하기 위한 관리 도구로 정의한다. 원본 데이터는 결론이 아니라 근거이며, 화면은 `어디에 문제가 있는가`, `왜 확인해야 하는가`, `무엇을 수정할 수 있는가`, `원본 근거는 무엇인가`를 한 흐름으로 제공해야 한다.

## 10. 선생님용 설명 언어 개편 적용

### 적용한 변경

- 첫 화면 제목을 `실제 데이터 대시보드`에서 `VR 안전교육 수업 점검판`으로 바꾸고, 처음 보는 사용자가 `수업 완료`, `필수 장비`, `조작·안내` 순서로 읽도록 안내 영역을 추가했다.
- 메뉴를 `전체 개요`, `세션 상세`, `시나리오·PPE`, `사용성·그랩`, `원본 이벤트`에서 `수업 현황`, `한 회차 살펴보기`, `안전장비 학습`, `조작·안내 점검`, `기술 근거`로 바꿨다.
- `Education`, `ConfinedSpace`, `PpeArea`, PPE enum, 이벤트 코드와 조작 결과를 교사가 이해할 수 있는 한국어로 표시한다. 기술 코드명은 근거 확인이 필요한 화면에 보조 정보로 유지한다.
- 첫 화면의 원본 이벤트 건수와 데이터 품질 정보는 `기술 기록 상태 보기 (담당자용)` 안으로 이동하고, 과정 완료와 마지막 도달 단계 등 수업 판단 정보를 먼저 표시한다.
- 각 상세 영역에 `어떻게 활용하나요?` 설명을 추가해 단계 체류시간, 장비 판단, 잡기 조작, 음성 종료 상태가 어떤 교육·콘텐츠 개선으로 이어지는지 제시한다.

### 근본 원인과 영향 범위

기존 화면은 실제 텔레메트리를 사람이 이해할 말로 바꿨지만, 기업이 수행하려는 업무 질문별 정보구조가 충분하지 않았다. 또한 현재 신호로 관찰 가능한 현상과 추가 계약 후 판정할 수 있는 원인을 한 화면에서 명확히 구분할 필요가 있었다.

변경 범위는 `server/public/dashboard/index.html`, `Assets/Scripts/PPETrainingTelemetryCapture.cs`, 대시보드 제공 테스트와 이 회의록이다. 텔레메트리에는 `session_started.appVersion`만 추가했으며 서버 API, 사용자 DB 스키마, 교육 상태 전이와 XR 입력 동작은 변경하지 않았다.

### Unity 변경 전 필수 질문 답변

1. 기존 Inspector/씬 작성값은 변경하지 않는다.
2. 버전 값의 소유자는 `PPETrainingTelemetryCapture.Record`, 기준 원본은 `Application.version`이다.
3. 입력 이벤트·Interactor·Caster·Raycaster·Layer·Collider 경로는 변경하지 않는다.
4. 버전 누락을 런타임에서 추정하거나 자동 수리하지 않는다. 기존 로그는 계속 미수집으로 남긴다.
5. 소비자는 로컬 JSONL과 대시보드 버전 집계뿐이며 UI·텔레포트·PPE Grab·거울·XR 양안 동작에는 영향을 주지 않는다.
6. 변경 전 기준은 기존 13개 세션에 버전 필드가 없는 상태다. 변경 후 비교 실행은 새 Unity 세션의 `session_started.appVersion` 확인이며 아직 실제 Play 로그가 필요하다.
7. 정적 코드·Unity 컴파일·계약 하네스까지 확인하고, Unity Play·Quest/OpenXR 새 세션 수집은 별도 수동 검증으로 남긴다.

### 완료한 검증

- 대시보드 JavaScript 구문 검사 통과
- 서버 자동 테스트 13건 통과
- 로컬 서버 health와 대시보드 HTTP 200 확인
- 실제 13개 세션의 이벤트 유형·필드와 대시보드 계산 입력을 대조
- Unity 명령 실행 시 C# 컴파일 성공
- `PPETrainingDataContractHarness.Validate()` PASS
- `DocumentationPolicyHarness.Validate()` PASS

### 아직 필요한 수동 검증

- 연결 가능한 브라우저 인스턴스가 없어 7개 메뉴 전환, 직원 세션 선택, 감사 로그 이동, 데스크톱·모바일 테이블 잘림은 수동 확인이 필요하다.
- 새 Unity Play/Quest 세션의 `session_started.appVersion`이 JSONL과 서버 조회에 나타나는지 확인해야 한다.
- 업데이트 비교, 회원사 조회, 공식 Test 결과, 원인별 이탈률은 서로 다른 버전 표본 또는 해당 데이터 계약을 구현하고 실제 Unity/Quest 로그와 서버 조회를 확인한 뒤에만 수치 검증할 수 있다.
