# 2026-08-21 PPE VR 훈련 사용자 데이터 대시보드 컨셉

## 1. 한 문장 컨셉

이 대시보드는 기업 단체 교육에서 직원이 PPE VR 교육과정을 **끝까지 이수했는지, 어디에서 막히거나 이탈했는지, 재이수 때 수행이 개선되었는지**를 직원별 반복 수행 기록과 조직 단위 집계로 확인하는 교육 운영·평가 근거·서비스 개선 도구다.

직원 평가 근거와 서비스 개선 분석을 분리한다. 직원 평가는 명확한 Test 결과, 점수·합격 규칙과 직원 식별·소속 연동이 있을 때만 사용하고, 콘텐츠 분석은 모드별 난이도와 동선·인터랙션·안내·학습 구조 중 어느 부분을 고쳐야 하는지 찾는 데 사용한다. 헬멧·장갑·마스크 등 개별 PPE 지표는 평가 점수와 서비스 병목 진단의 근거를 구분해 표시한다.

## 2. 분석 대상

대상 앱은 기업 단체 직원이 수행하는 PPE 안전교육 VR 콘텐츠다. 배포 채널이 Meta Horizon이더라도 대시보드의 관리 단위는 기업 교육 대상자와 반복 교육 세션이며, 사용자는 같은 PPE 절차를 다음 세 모드에서 반복 수행한다.

| 모드 | 분석 목적 | 주요 질문 |
| --- | --- | --- |
| Learning | 안내를 받으며 개념과 절차를 익히는 단계 | 사용자가 무엇을 보고 듣고 따라 하는가? |
| Training | 힌트를 줄이며 수행 방법을 연습하는 단계 | 안내가 줄어도 수행이 안정되는가? |
| Test | 도움 없이 학습 결과를 확인하는 단계 | 사용자가 독립적으로 통과하는가? |

대시보드는 한 직원의 여러 회차 기록을 연결해 학습 곡선을 보고, 직원 디렉터리와 조직 정보가 연결된 뒤에는 부서·교육 기수·전체 대상자 집계와 비교한다.

## 3. 대시보드의 기본 필터

지표가 무엇을 기준으로 계산되었는지 혼동하지 않도록 다음 축을 분리한다.

- 사용자 범위: 전체 사용자 / 특정 사용자
- 수행 모드: Learning / Training / Test
- 콘텐츠: 헬멧 / 장갑 / 마스크 등 PPE별 태스크
- 시간 범위: 회차별 / 날짜별 / 첫 수행 대비 최근 수행

따라서 “평균 수행시간”은 모호한 전체 평균이 아니라, 예를 들어 **사용자 A의 Training 장갑 착용 태스크 3회 평균**처럼 범위를 명시한다.

### 3.1 콘텐츠 분석과 공간 분석의 차이

두 분석은 같은 플레이 이벤트를 서로 다른 기준으로 묶어 보는 것이다.

| 구분 | 무엇을 기준으로 묶는가 | 답하려는 질문 | 예시 |
| --- | --- | --- | --- |
| 콘텐츠 분석 | 어떤 PPE·태스크·절차를 수행했는가 | 마스크 착용 태스크 자체가 어려운가? | 마스크 통과율, 장갑 Grab 실패율, PPE별 수행시간 |
| 공간 분석 | 씬의 어느 World 위치·voxel에서 행동했는가 | 룸의 어느 위치에서 찾기·조작·이동이 막히는가? | PPE 진열 영역의 예상 탐색구역 이탈, 거울 앞 정지, 복귀 앵커 주변 재탐색 |

예를 들어 사용자가 `PPE_A_Mask_Clean`을 잡으려다 실패했다고 하자.

- 콘텐츠 화면에서는 “마스크 태스크에서 Grab 실패 2회, 성공까지 18초”로 집계한다.
- 공간 화면에서는 “PPE 선택 영역의 X/Y/Z voxel에서 Grab 실패가 발생했고, 실패 당시 손과 marker의 거리가 얼마였는가”로 집계한다.

즉 콘텐츠 분석은 **무엇을 수행했는지**, 공간 분석은 **어디에서 수행했는지**를 본다. 하나의 이벤트에 `contentId`와 `voxelId`를 함께 저장하면 두 화면에서 같은 원시 데이터를 다르게 집계할 수 있다.

## 4. 흐름·인터랙션 UX 분석

### 4.1 발견성: 사용자가 대상을 찾았는가

`넓은 시선`, `주변을 많이 봄`, `시선이 산만함`처럼 기준이 없는 표현은 지표명과 판정 문구로 사용하지 않는다. 발견성은 **목표를 찾기 전 머리 방향 탐색이 단계별 예상 탐색구역을 얼마나 벗어났는지**, 목표가 실제 화면에 노출된 뒤에도 상호작용하지 못했는지, 잘못된 대상을 선택했는지를 함께 본다.

#### 4.1.1 실제 눈 시선과 HMD 머리 방향의 구분

- eye tracking 하드웨어, 런타임 권한, 보정 상태와 API가 모두 확인된 경우에만 눈동자 기반 데이터를 `gaze` 또는 `eyeGaze`라고 부른다.
- eye tracking을 사용하지 않는 실행에서는 `XR Camera`의 정면 벡터를 **HMD 머리 방향** 또는 `headForward`로 기록한다. 이를 사용자의 실제 눈 시선이라고 표현하지 않는다.
- 컨트롤러·손 Ray 방향은 사용자가 가리키려는 입력 방향이며, 머리 방향이나 눈 시선과 별도 필드로 저장한다.
- 장치·권한에 따라 측정 수단이 달라지므로 모든 이벤트에 `trackingSource=head|eye|controllerRay`를 명시한다. 서로 다른 tracking source의 결과를 같은 평균으로 합치지 않는다.

현재 프로젝트의 기본 지표는 별도의 eye tracking을 전제하지 않는 `headForward` 기반 머리 탐색이다. 향후 eye tracking을 추가하더라도 기존 머리 방향 지표와 이름·분모·동의 범위를 분리한다.

#### 4.1.2 발견 구간의 시작과 종료

단계마다 사용자가 탐색을 시작할 수 있는 시점이 다르므로 `task_presented`를 무조건 시작점으로 쓰지 않는다. 각 checkpoint에 `discoveryStartEvent`를 작성한다.

| 상황 | 발견 구간 시작 | 발견 구간 종료 |
| --- | --- | --- |
| 안내를 들으면서 바로 탐색할 수 있음 | `task_presented` | 첫 유효 목표 상호작용 |
| 안내가 끝날 때까지 입력이 차단됨 | `guidance_completed` | 첫 유효 목표 상호작용 |
| 시각 안내가 켜진 뒤 탐색 가능 | `visual_guidance_shown` | 첫 유효 목표 상호작용 |

첫 유효 목표 상호작용은 현재 단계의 정상 목표에 대한 `target_hover_started`, 올바른 대상 `grab_attempted` 또는 `select_attempted` 중 가장 먼저 발생한 이벤트다. `target_hover_started`가 컨트롤러 Ray 기반이라면 이는 **목표를 바라봤다는 증거가 아니라 목표를 처음 유효하게 가리킨 시점**으로 해석한다.

다음 시간은 발견 구간에서 제외하거나 별도 상태로 분리한다.

- 씬 로드, 화면 페이드와 입력 차단 시간
- 필수 TTS를 듣는 동안 탐색이 허용되지 않은 시간
- 앱 pause, focus 상실과 시스템 메뉴 표시 시간
- 텔레포트 또는 자동 이동 중 카메라가 강제로 회전한 시간
- 목표 오브젝트가 비활성이거나 실제로 가려져 접근할 수 없는 시간

#### 4.1.3 단계별 예상 탐색구역

`넓다`는 절대 각도로 정의하지 않고 **현재 checkpoint에서 사용자가 합리적으로 찾아볼 것으로 설계된 방향 범위**와 비교한다. 각 checkpoint에는 다음 분석 설정을 씬·프리팹 또는 별도 직렬화 설정으로 작성한다.

```text
checkpointId
targetId / targetBounds
searchReference: taskStartPose | authoredAnchor | currentHeadPose
expectedYawMin / expectedYawMax
expectedPitchMin / expectedPitchMax
discoveryStartEvent
visibilityCheckMode
```

시작 위치가 고정이면 작성된 시작 Anchor와 목표 Bounds를 기준으로 예상 구역을 만든다. 시작 위치가 달라질 수 있으면 태스크 시작 순간의 HMD 위치에서 목표 Bounds를 향한 상대 각도를 계산한다. 벽·다른 PPE·패널 때문에 목표가 가려지는 경우에는 카메라 frustum 포함 여부만으로 `보였다`고 판정하지 않고, 가능한 경우 목표 Bounds까지의 line-of-sight 또는 occlusion 검사를 함께 사용한다.

예상 yaw·pitch 범위는 표시용 UI 값이 아니라 분석 계약이다. 임의 기본값으로 모든 단계에 동일 적용하지 않고, 단계별 시작 Pose·목표 크기·실제 룸 배치를 확인해 작성한다.

#### 4.1.4 수집값과 계산식

발견 구간이 끝나면 매 프레임 원시 머리 궤적 대신 다음 요약값을 `head_search_summary` 이벤트로 저장한다. 샘플링 주기, 최소 각도 변화와 angular bin 크기는 분석 설정으로 두고 기준 실행 전에는 판정 임계값으로 사용하지 않는다.

| 필드 | 계산 방식 | 해석 |
| --- | --- | --- |
| `discoveryDuration` | 유효 발견 구간 종료 - 시작 | 목표와 처음 상호작용하기까지의 시간 |
| `headYawP05P95Span` | yaw의 5~95 percentile 범위 | 순간 jitter와 극단값을 줄인 좌우 머리 탐색 범위 |
| `headPitchP05P95Span` | pitch의 5~95 percentile 범위 | 순간 jitter와 극단값을 줄인 상하 머리 탐색 범위 |
| `cumulativeHeadRotation` | 유효 샘플 사이 각도 변화의 합 | 반복적인 머리 탐색의 총량 |
| `visitedAngularBinCount` | 방문한 yaw·pitch bin 수 | 서로 다른 방향 구역을 탐색한 정도 |
| `directionReversalCount` | yaw 또는 pitch 진행 방향이 유효 문턱 이상 반전된 횟수 | 같은 구간을 오가며 찾는 패턴 |
| `outsideExpectedRegionDuration` | 예상 yaw·pitch 구역 밖의 유효 시간 | 설계된 탐색구역을 벗어난 시간 |
| `outsideExpectedRegionRatio` | 구역 밖 시간 / 유효 발견시간 | 회차 길이가 다른 사용자 간 비교용 비율 |
| `targetInViewDuration` | frustum·가시성 검사를 통과한 시간 | 목표가 화면에 노출된 시간 |
| `targetVisibleUnengagedDuration` | 첫 유효 상호작용 전 가시성 검사를 통과한 구간의 누적시간 | 보였지만 목표로 인식·선택하지 못한 가능성 |
| `wrongTargetInteractionCount` | 발견 구간 중 잘못된 목표 상호작용 수 | 인접 대상 혼동 가능성 |

`headYawSpanP95`나 `visitedAngularBinCount`가 크다는 사실만으로 UX 문제라고 판정하지 않는다. 다음 신호가 같은 checkpoint에서 여러 사용자에게 함께 반복될 때만 **발견성 설계 검토 후보**로 표시한다.

```text
예상 탐색구역 이탈이 큼
AND 목표 발견시간이 김
AND 잘못된 대상 상호작용 또는 방향 반전이 반복됨
```

목표가 화면에 충분히 노출됐는데도 상호작용하지 못한 시간이 길다면 오브젝트 외형·라벨·강조·조작 가능성 표현을 우선 조사한다. 목표 자체가 화면에 거의 들어오지 않았다면 시작 방향, 배치, 높이, 가림, 안내 방향을 우선 조사한다. 머리 탐색 범위가 넓어도 목표를 빠르게 찾고 정상 진행했다면 정상적인 주변 확인으로 남기고 결함 후보로 표시하지 않는다.

절대 각도·시간 문턱은 사전에 임의로 정하지 않는다. 첫 기준 실행과 초기 사용자 수행에서 checkpoint별 분포, 성공 수행의 중앙값과 P90, 실제 표본 수를 표시한 뒤 검토 기준을 확정한다. 표본이 적을 때는 정상·비정상 라벨 대신 원시 요약값과 사용자별 수행 흔적만 보여 준다.

### 4.2 이해성: 무엇을 해야 하는지 이해했는가

- 현재 태스크를 시작한 뒤 첫 행동까지의 시간
- TTS·시각 안내·하이라이트가 노출되었는지
- 안내 반복 요청 또는 안내 재생 후 정지 시간
- 다음 태스크로 넘어가지 못한 횟수
- 완료 후 다음 행동을 기다린 시간

TTS가 재생되었는데도 못 찾은 경우는 음성만의 문제로 단정하지 않는다. 음성, 화면 UI 위치, 오브젝트 배치, 사용자의 머리 방향 탐색과 실제 상호작용이 함께 영향을 주므로 대시보드에서는 이를 **안내 패키지 노출 후 수행 결과**로 표현한다. eye tracking을 실제로 사용한 회차만 눈 시선 데이터로 별도 표시한다.

### 4.3 인터랙션: 조작할 수 있었는가

- 잘못된 레이 대상 적중
- 올바른 대상에 대한 Grab 시도와 실패
- marker 근처까지 접근했지만 손이 닿지 않은 경우
- 잘못된 손 또는 잘못된 방향으로 잡은 경우
- 반복 조작 횟수와 성공까지 걸린 시간

“잘못된 행동 비율” 하나로 묶지 않고 다음과 같이 구분한다.

| 관찰 패턴 | 가능한 해석 | 개선 방향 |
| --- | --- | --- |
| 목표 노출이 적고 예상 탐색구역 이탈이 큼 | 대상을 못 찾음 | 배치·시작 방향·가림·시각 안내 개선 |
| 대상은 찾았지만 marker 주변 Grab 실패 반복 | 인터랙션 수행이 어려움 | marker 크기·거리·손 입력 개선 |
| 잘못된 PPE를 반복 선택 | 상태·절차를 이해하지 못함 | 하자/정상품 구분과 피드백 개선 |
| 성공 후 다음 태스크에서 장시간 정지 | 흐름 연결이 약함 | 다음 단계 안내·완료 피드백 개선 |

### 4.4 흐름 연결: 다음 행동으로 넘어갔는가

- 태스크 완료 후 다음 태스크 시작까지의 시간
- 이전 태스크로 되돌아간 횟수
- 중단 후 복귀한 위치와 재개까지 걸린 시간
- 텔레포트 또는 이동 중단 횟수
- 현재 단계와 다음 단계 사이에서 발생한 반복 행동

텔레포트는 항상 실패가 아니다. 중도 중단 후 복귀를 위한 정상 행동인지, 공간을 찾지 못해 반복 이동한 것인지 상태와 함께 기록한다.

## 5. 학습·수행 분석

### 5.1 사용자별 학습 곡선

사용자 한 명의 여러 회차를 연결해 다음 변화를 본다.

- 첫 시도에서 통과까지 걸린 시간의 변화
- 같은 PPE의 반복 오류 감소 여부
- 힌트·TTS·시각 안내 의존도 감소 여부
- Learning에서 Training, Test로 이동했을 때 수행 유지 여부
- 특정 단계에서 계속 반복되는 병목

차트는 회차를 가로축으로 두고 수행시간, 오류 횟수, 힌트 사용, 태스크 통과 여부를 함께 표시한다. 이를 통해 한 번의 점수보다 **학습을 통해 개선되었는지**를 확인한다.

### 5.2 모드별 수행

- Learning: 안내를 받은 상태에서 절차를 이해하는지 확인
- Training: 도움을 줄여도 수행이 유지되는지 확인
- Test: 도움 없이 독립적으로 통과하는지 확인

마스크 착용처럼 통과/실패가 명확한 태스크는 정확도 평균으로 표시하지 않는다. 실제 데이터에는 `passed: true/false`를 별도 기록하고, 대시보드에는 **태스크 통과율**과 **테스트 무도움 통과율**을 표시한다.

“무도움 테스트”는 Test 모드에서 힌트·추가 안내·재생 요청 없이 태스크를 수행한 경우로 정의한다. Learning이나 Training의 점수와 섞지 않는다.

### 5.3 콘텐츠별 수행

PPE별 수행 화면에서는 헬멧·장갑·마스크 등의 콘텐츠 차이를 비교한다.

단, PPE별 완료율 자체를 교육성과로 해석하지 않는다. 최상위 화면에서는 전체 과정 이수 여부, 마지막 도달 단계, 중도 이탈 지점, 재이수 개선 여부와 모드별 난이도를 먼저 보여 주고, PPE별 수치는 특정 병목의 원인을 조사할 때만 상세 화면에서 사용한다.

- 콘텐츠별 태스크 통과율
- 첫 시도 성공률
- 평균 수행시간
- 잘못된 선택과 Grab 실패
- 다음 태스크 연결 실패
- 동일 사용자의 반복 개선 여부

콘텐츠별 수행도와 전체 동선 UX는 별도 화면으로 둔다. 장갑의 Grab이 어려운 문제와 전체 절차가 복잡한 문제는 서로 다른 개선 대상이기 때문이다.

## 6. 공간 데이터 시각화 컨셉

공간 데이터는 얇은 2D 레이어를 겹치는 방식이 아니라, Unity 씬의 실제 유효 공간을 기준으로 한 3D voxel 구조로 분석한다.

### 6.1 씬 기준

현재 기준 씬은 `Assets/Scenes/3_PPE_Room_Train_Test_mask.unity`다.

- Floor Bounds를 기준으로 PPE Room의 World 공간을 확인한다.
- Floor·Ceiling·Collider·NavMesh를 이용해 분석 셀의 범위와 유효 여부를 계산한다.
- 셀 크기에 따라 X/Y/Z 개수가 결정되며, 임의의 3×3×3을 고정하지 않는다.
- 각 셀은 X/Y/Z 인덱스와 World AABB 범위를 가진다.

### 6.2 영역 매핑

각 셀에 단순 이벤트 수만 표시하지 않고, 씬 안에서 어떤 의미를 갖는지 연결한다.

| 공간 영역 | 연결 대상 | 분석 목적 |
| --- | --- | --- |
| PPE 선택·Grab | PPE marker와 진열 PPE | 대상 발견과 손 조작 난이도 분석 |
| 거울 확인 | `PPE_Room_Planar_Mirror` | 착용 확인과 시선 유지 분석 |
| 중단 복귀 | `PPE_2 Arrival Anchor` | 중단 후 재개와 복귀 동선 분석 |
| 출구·다음 이동 | `PPE Room Door Image` | 다음 단계 연결과 이동 흐름 분석 |
| 주 이동 공간 | Room Floor·Collider | 레이·이동·정지 행동의 기준 공간 |

최종 화면에서는 큐브 내부에 영역명, 외부 축 눈금, World 좌표 범위, 근거 오브젝트 범례가 지속적으로 보여야 한다. 셀을 클릭했을 때만 위치를 알 수 있는 방식은 충분하지 않다.

### 6.3 공간 이벤트

셀별로 다음 이벤트를 집계한다.

- 레이 발사·적중·오적중
- hover·highlight
- Grab 시도·성공·실패
- 태스크 시작·완료·중단
- 정지 시간
- 텔레포트 시작·도착·취소
- 다음 태스크 연결 성공·대기·되돌아감

공간 히트맵의 색은 이벤트 밀도와 실패 집중도를 표현하고, 특정 셀을 선택하면 해당 셀의 영역·좌표·대표 오브젝트·행동 해석을 함께 보여 준다.

## 7. 수집할 원시 이벤트 구조

각 이벤트에는 최소한 다음 정보를 포함한다.

```text
userId / sessionId / attemptId
mode / contentId / taskId
timestamp / elapsedTime
eventType / targetId / outcome
worldPosition / voxelIndex
guidanceState / ttsPlayed / visualHintShown
taskState / previousTaskId / nextTaskId
trackingSource / discoveryStartEvent
```

원시 손·머리 궤적을 전부 저장하기보다, 분석에 필요한 이벤트와 위치를 중심으로 수집한다. 머리 방향 탐색은 발견 구간 종료 시 `head_search_summary` 요약값을 우선 저장하고, 필요할 때만 사용자 동의를 거쳐 짧은 시간 구간의 원시 궤적을 추가해 저장량과 개인정보 노출을 줄인다.

### 7.1 실제 수집 시점과 이벤트

아래는 PPE 하나를 수행할 때의 실제 이벤트 흐름이다. 매 프레임의 모든 손·머리 위치를 저장하지 않고, 상태가 바뀌거나 의미 있는 조작이 발생한 순간에 기록한다.

| 발생 시점 | 이벤트명 | 기록할 내용 | 주로 쓰는 분석 |
| --- | --- | --- | --- |
| 이름 입력과 초기화가 끝난 순간 | `session_started` | 익명 사용자 ID, session ID, 씬, 앱 버전 | 세션 수, 이탈률 |
| Learning/Training/Test를 선택한 순간 | `mode_selected` | mode, scenario ID | 모드별 비교 |
| 한 PPE 태스크가 활성화된 순간 | `task_presented` | content ID, task ID, step index, 목표 오브젝트 ID | 콘텐츠별 시작 수, 태스크 노출 수 |
| TTS 재생을 시작한 순간 | `tts_started` | TTS clip ID, 안내 단계 | 안내 노출 여부 |
| TTS가 끝난 순간 | `tts_completed` | clip ID, 재생 시간 | 안내 후 첫 행동까지의 시간 |
| 시각 UI·하이라이트가 켜진 순간 | `visual_guidance_shown` | UI ID, target ID, hint level | 안내 패키지 노출 |
| 컨트롤러·손 Ray가 정상 대상에 처음 일정 시간 이상 머문 순간 | `target_hover_started` | tracking source, ray origin/direction, hit target, World 위치, voxel ID | 목표를 처음 유효하게 가리킨 시간 |
| 대상에서 레이가 벗어난 순간 | `target_hover_ended` | target ID, hover duration | 대상 인식 유지 시간 |
| 대상이 아닌 Collider·PPE에 레이가 적중한 순간 | `wrong_ray_hit` | hit object, World 위치, voxel ID | 발견성·배치 문제 |
| 발견 구간이 첫 유효 목표 상호작용 또는 중단으로 끝난 순간 | `head_search_summary` | discovery start/end, tracking source, yaw/pitch P05~P95 범위, 누적 회전, 예상 구역 이탈시간·비율, 목표 노출시간, 방향 반전, 오상호작용 수 | 발견성 설계 검토 |
| Grab/Select를 누른 순간 | `grab_attempted` | hand, target ID, hand World 위치, voxel ID | 조작 시도 수 |
| Grab 결과가 확정된 순간 | `grab_succeeded` 또는 `grab_failed` | 실패 코드, marker와 손 거리, hand, target | 인터랙션 난이도 |
| 검사 동작이 시작된 순간 | `inspection_started` | content ID, 검사 방식, 위치·voxel | 검사 진입률 |
| 몸에 대고 착용 Trigger를 누른 순간 | `equip_attempted` | target ID, attach point, 거리, mode | 착용 시도 |
| 착용 판정이 끝난 순간 | `equip_approved` 또는 `equip_rejected` | 결과, error code, content ID | 절차·상태 이해 |
| PPE 착용 상태가 실제로 변경된 순간 | `task_completed` | content ID, 수행시간, 결과, 다음 task ID | 콘텐츠 통과율·수행시간 |
| 다음 태스크가 활성화된 순간 | `next_task_available` | previous task ID, next task ID | 흐름 연결 |
| 다음 태스크의 첫 유효 행동이 발생한 순간 | `next_task_started` | next task ID, 첫 행동 이벤트 | 다음 단계 연결 시간 |
| 텔레포트가 시작·도착·취소된 순간 | `teleport_started`, `teleport_arrived`, `teleport_cancelled` | 시작/도착 위치, voxel ID, 결과 | 공간 이동·복귀 분석 |
| 사용자가 명시적으로 나가거나 세션이 종료된 순간 | `attempt_ended`, `session_ended` | 종료 원인, 마지막 task, 마지막 voxel | 중도 이탈·중단 분석 |

### 7.2 한 이벤트에 공통으로 들어갈 필드

이벤트 종류가 달라도 다음 컨텍스트는 공통으로 넣는다.

| 필드 묶음 | 필드 | 설명 |
| --- | --- | --- |
| 식별 | `userId`, `sessionId`, `attemptId`, `eventId` | 익명 사용자와 수행 회차 연결 |
| 수행 맥락 | `sceneId`, `scenarioId`, `mode`, `contentId`, `taskId`, `stepIndex` | 어느 상황·모드·콘텐츠의 이벤트인지 구분 |
| 시간 | `timestamp`, `elapsedFromAttempt`, `duration` | 실제 시각과 태스크 내 경과시간 |
| 행동 | `eventName`, `actor`, `targetId`, `outcome`, `errorCode` | 무엇을 누르고 무엇이 성공·실패했는지 |
| 공간 | `worldPosition`, `voxelId`, `regionId` | 발생 위치와 씬 영역 연결 |
| 안내 상태 | `ttsClipId`, `visualHintId`, `hintLevel` | TTS·UI 안내가 노출된 상태 기록 |
| 탐색 맥락 | `trackingSource`, `discoveryStartEvent`, `expectedSearchRegionId` | 실제 눈 시선, HMD 머리 방향과 컨트롤러 Ray를 구분하고 단계별 예상 탐색구역 연결 |

손·머리 궤적은 모든 프레임을 저장하지 않는다. `grab_attempted`, `equip_attempted`, `wrong_ray_hit`, `teleport_*`처럼 해석에 필요한 순간에만 위치를 저장하고, 레이 탐색처럼 연속적인 행동은 태스크 종료 시 횟수·최초 위치·최종 위치·voxel별 집계로 저장한다. HMD 머리 방향은 발견 구간 동안 일시적으로 계산하되 기본 전송값은 `head_search_summary`의 요약 통계로 제한한다.

### 7.3 실제 데이터에서 계산할 지표

원시 이벤트를 쌓은 뒤 대시보드에서 다음과 같이 계산한다.

| 지표 | 계산 방식 | 의미 |
| --- | --- | --- |
| 대상 발견 시간 | 첫 유효 목표 상호작용 - checkpoint별 `discoveryStartEvent` | 실제 탐색이 허용된 뒤 목표를 가리키거나 조작하기까지의 시간 |
| 예상 탐색구역 이탈률 | `outsideExpectedRegionDuration` / 유효 발견시간 | 설계된 탐색 방향을 벗어난 정도를 나타내는 보조 지표 |
| 목표 노출 후 미상호작용 시간 | 첫 유효 목표 상호작용 전 목표가 실제로 보인 구간의 누적시간 | 보였지만 목표로 인식하거나 조작하지 못한 가능성 |
| Grab 성공률 | `grab_succeeded` / `grab_attempted` | 조작 자체의 난이도 |
| 착용 통과율 | `equip_approved` / `equip_attempted` 또는 태스크 기준 Boolean 통과 | 착용 판정 결과 |
| 콘텐츠 수행시간 | `task_completed` - `task_presented` | 특정 PPE 태스크의 소요시간 |
| 다음 단계 연결 시간 | `next_task_started` - `next_task_available` | 완료 후 다음 행동으로 넘어가는 시간 |
| 공간 오적중 밀도 | voxel별 `wrong_ray_hit` / 해당 voxel 활성시간 | 특정 위치의 탐색·배치 문제 |
| 학습 개선량 | 같은 사용자의 첫 회차와 최근 회차의 시간·오류·통과 변화 | 반복 수행에 따른 개선 |

`task_completed`는 단순히 Trigger를 눌렀다는 뜻이 아니라, 현재 PPE 상태가 실제 착용 완료 상태로 바뀌었다는 앱 상태를 기준으로 발생시킨다. 마스크처럼 통과/실패가 명확한 태스크는 `passed: true/false`를 별도로 기록하고 정확도 평균으로 변환하지 않는다.

### 7.4 마스크 착용 1회 예시

마스크 태스크 한 번은 다음과 같이 기록될 수 있다.

```text
task_presented(contentId=mask, taskId=mask_donning)
tts_started(clipId=EDU_202)
visual_guidance_shown(targetId=PPE_A_Mask_Clean)
wrong_ray_hit(hitObject=PPE_A_Goggle_Clean, voxelId=X5-Y1-Z8)
target_hover_started(targetId=PPE_A_Mask_Clean, voxelId=X5-Y1-Z8)
grab_attempted(hand=right, targetId=PPE_A_Mask_Clean, voxelId=X5-Y1-Z8)
grab_succeeded(hand=right, targetId=PPE_A_Mask_Clean)
equip_attempted(targetId=PPE_A_Mask_Clean, distance=0.18)
equip_approved(contentId=mask, passed=true)
task_completed(contentId=mask, duration=63s, nextTaskId=mirror_check)
next_task_available(nextTaskId=mirror_check)
next_task_started(nextTaskId=mirror_check)
```

이 기록으로 콘텐츠 화면은 마스크의 수행시간·통과 여부·오선택을 보여 주고, 공간 화면은 `X5-Y1-Z8`에서 잘못된 레이와 실제 Grab이 발생했다는 사실을 보여 준다.

## 8. 대시보드가 실제 개선으로 연결되는 방식

대시보드는 다음과 같은 질문에 답해야 한다.

1. 사용자가 대상을 못 찾은 것인가, 찾았지만 조작하지 못한 것인가?
2. TTS와 UI 안내가 노출되었는데도 다음 행동으로 연결되지 않은 것인가?
3. 특정 PPE의 문제인가, 전체 동선의 문제인가?
4. Learning에서는 성공하지만 Test에서 무너지는가?
5. 한 사용자만의 문제인가, 여러 사용자에게 반복되는 구조적 문제인가?
6. 중단 후 복귀가 정상적으로 이어지는가?

예를 들어 장갑 영역에서 레이 오적중은 적지만 marker 근처 Grab 실패가 반복되면, 안내 문제가 아니라 손 입력·거리·marker 설계 문제로 볼 수 있다. 반대로 대상 주변에 도착하기 전 레이가 넓게 분산되고 다음 태스크 연결 전 정지가 길다면, 공간 배치나 안내 흐름을 우선 개선한다.

- 화면 기본값은 실명 대신 익명화된 직원·앱 사용자 ID를 사용하고, 권한이 있는 기업 교육관리 시스템에서만 사번·소속과 연결한다.

- 안내 효과를 비교하려면 별도의 실험군·대조군 또는 안내 조건 기록이 필요하다.
- 테스트 통과 여부는 명확한 Boolean 결과로 기록하고, 평균 정확도로 대체하지 않는다.

## 13. 2026-08-24 선생님 피드백 반영: 실무 활용과 확정 지표

### 13.1 지적 내용과 보완 방향

기존 설명은 수집 가능한 행동과 시각화 아이디어를 나열했지만, 각 수치가 실제로 어떤 수정 결정에 쓰이는지가 충분히 명확하지 않았다. 특히 3D voxel 자체가 결과물처럼 보였고, 공간 지표와 콘텐츠 지표가 어떤 실무 문제를 분리하는지 설명이 약했다.

이후 대시보드는 다음 원칙을 따른다.

1. 지표마다 분자, 분모, 집계 대상, 시간 범위를 명시한다.
2. 지표마다 그 결과로 수정할 수 있는 대상이 하나 이상 연결되어야 한다.
3. 단순 조회 수치보다 수정 전후 비교가 가능한 수치를 우선한다.
4. 공간 분석은 이름이 있는 작업 구역을 우선 사용하고, voxel은 구역 내부의 세부 위치를 좁힐 때만 사용한다.
5. `passed`는 앱의 태스크 판정 결과인 Boolean 값으로 직접 기록한다. `accuracy` 점수나 임의 기준값으로 환산하지 않는다.
6. 레이 방향 분산, hover 횟수, 단순 이벤트 수처럼 해석이 여러 개인 값은 핵심 성과지표로 사용하지 않고 원인 조사용 보조 지표로 둔다.

### 13.2 공간 분석의 실무 지표

공간 분석은 “어디에서 문제가 많이 발생했는가”에 그치지 않고, 오브젝트 배치·도달 거리·이동 동선 중 무엇을 수정할지 결정해야 한다.

| 지표 | 계산 기준 | 지표로 판단할 문제 | 연결되는 수정 대상 |
| --- | --- | --- | --- |
| 대상 발견시간 | 첫 유효 목표 상호작용 시각 - checkpoint별 `discoveryStartEvent` 시각 | 사용자가 PPE 위치를 찾기 어려운가 | PPE 위치, 높이, 조명, 표지판, 시작 방향 유도 |
| 예상 탐색구역 이탈률 | 발견 구간 중 예상 yaw·pitch 범위 밖 시간 / 유효 발견시간 | 사용자가 설계된 방향과 다른 곳을 반복 탐색하는가 | 시작 Pose, 배치, 가림, 안내 방향 |
| 목표 노출 후 미상호작용 시간 | 목표 가시성 시작 - 첫 유효 목표 상호작용 | 목표가 보여도 조작 대상으로 이해하지 못하는가 | 외형 구분, 라벨, highlight, affordance |
| 오선택률 | 잘못된 PPE 선택이 발생한 수행 수 / 전체 선택 수행 수 | 인접 PPE가 혼동되는가 | PPE 간격, 외형 구분, 라벨, 진열 순서 |
| 근접 Grab 실패율 | marker 기준 거리 안에서 발생한 `grab_failed` 수 / 같은 거리 안의 전체 Grab 시도 수 | 대상을 찾았지만 손으로 조작하기 어려운가 | marker 크기·위치, Collider, Interaction Layer, 도달 거리 |
| 구역 정체율 | 구역 진입 후 기준시간 이상 다음 유효 행동이 없었던 수행 수 / 해당 구역 진입 수행 수 | 공간에 도착한 뒤 무엇을 해야 할지 모르는가 | 구역 안내, 오브젝트 방향, 다음 단계 표시 |
| 다음 구역 전환 실패율 | 태스크 완료 후 기준시간 안에 다음 구역 행동이 시작되지 않은 수행 수 / 태스크 완료 수행 수 | 거울·출구·복귀 지점으로 연결되지 않는가 | 다음 단계 안내, 출구 위치, Arrival Anchor, 텔레포트 지점 |
| 우회 이동률 | 실제 이동거리 / 동일 시작·도착점의 기준 동선 거리 | 장애물 또는 이동 지점 때문에 불필요한 이동이 생기는가 | 장애물 배치, 이동 가능 영역, 텔레포트 목적지 |

공간 집계의 1차 단위는 다음 이름 기반 구역으로 한다.

- PPE 진열·선택 구역
- 장갑·마스크 등 PPE별 Grab 구역
- 착용 판정 구역
- 거울 확인 구역
- 중단 복귀 구역
- 출구·다음 단계 이동 구역

voxel은 위 구역 중 어느 높이와 위치에서 Grab 실패나 정체가 집중되는지 추가로 좁힐 때만 사용한다. 전체 voxel을 동일한 중요도로 보여 주는 것은 우선 구현 범위에서 제외한다.

### 13.3 콘텐츠 분석의 실무 지표

콘텐츠 분석은 공간 위치와 무관하게 특정 PPE의 절차·판정·안내가 실제 학습으로 이어지는지 판단한다.

| 지표 | 계산 기준 | 지표로 판단할 문제 | 연결되는 수정 대상 |
| --- | --- | --- | --- |
| 태스크 통과율 | `passed=true` 태스크 수 / `task_presented` 태스크 수 | 절차와 완료 조건을 수행할 수 있는가 | 판정 조건, 절차 구성, 난이도 |
| 첫 시도 통과율 | 첫 시도에서 통과한 사용자 수 / 첫 시도를 시작한 사용자 수 | 최초 안내만으로 수행 가능한가 | 튜토리얼, 최초 지시, 예시 |
| Test 무도움 통과율 | 힌트 0회이고 `passed=true`인 Test 수 / 전체 Test 수 | Training 결과가 독립 수행으로 전이되는가 | Training 안내 단계, 힌트 감소 방식 |
| 오류 유형별 발생률 | 해당 `errorCode`가 한 번 이상 발생한 수행 수 / 전체 수행 수 | 어떤 절차 오류가 반복되는가 | 단계별 피드백, 검사 순서, 판정 설명 |
| 통과 수행시간 | 통과한 태스크의 중앙값과 P90 수행시간 | 일부 사용자가 특정 절차에서 지나치게 오래 걸리는가 | 단계 수, 조작 복잡도, 안내 시점 |
| 태스크 중단률 | 정상 완료되지 않은 태스크 수 / 시작된 태스크 수 | 사용자가 어느 콘텐츠에서 이탈하는가 | 해당 단계 난이도, 오류 회복, 중단·복귀 처리 |
| 학습 전이율 | Training 통과 후 Test를 무도움으로 통과한 동일 사용자 수 / Training 통과 후 Test를 수행한 사용자 수 | 연습 성공이 실제 학습으로 이어지는가 | Learning·Training 구성과 Test 난이도 |

평균만 표시하지 않고 표본 수, 중앙값, P90을 함께 표시한다. Learning·Training·Test는 목적이 다르므로 하나의 전체 평균으로 합치지 않는다.

### 13.4 공간 문제와 콘텐츠 문제의 구분 예시

마스크 태스크 통과율이 낮은 경우에도 실패 원인에 따라 수정 대상은 달라진다.

| 확인 결과 | 문제 분류 | 실무 조치 |
| --- | --- | --- |
| 마스크 발견시간이 길고 오선택이 진열 구역에 집중됨 | 공간 배치·구분 문제 | 마스크 위치, PPE 간격, 라벨 수정 |
| 마스크는 빠르게 찾지만 marker 근처 Grab 실패가 반복됨 | 인터랙션 문제 | marker·Collider·도달 거리 수정 |
| Grab은 성공하지만 잘못된 순서로 착용함 | 콘텐츠 절차 문제 | 절차 안내와 오류 피드백 수정 |
| Learning 통과율은 높지만 Test 무도움 통과율이 낮음 | 안내 의존·학습 전이 문제 | Training의 힌트 감소 방식 수정 |
| 착용은 완료하지만 거울 또는 다음 태스크로 이동하지 않음 | 흐름 연결 문제 | 완료 피드백과 다음 구역 안내 수정 |

따라서 “마스크 실패” 하나로 보고하지 않고, `발견 → 조작 → 절차 → 통과 → 다음 단계 연결` 중 어느 구간에서 실패했는지를 지표로 분리한다.

### 13.5 실무 적용 절차

1. 태스크 통과율 또는 다음 단계 연결률이 낮은 PPE를 찾는다.
2. 이름 기반 공간 구역과 오류 유형별 지표로 원인 가설을 하나 선택한다.
3. PPE 위치, marker, Collider, 안내 또는 판정 조건 중 한 소비자만 수정한다.
4. 같은 조건으로 수정 전후 지표를 비교한다.
5. 목표 지표가 개선되지 않으면 원인 가설을 폐기하고 다음 후보를 조사한다.

실무 보고는 다음 형식으로 작성한다.

> 장갑 태스크 통과율은 78%였지만, PPE 진열 구역에서 장갑을 발견한 수행 중 31%가 marker 기준 거리 안에서 Grab에 실패했다. 따라서 안내 문제가 아니라 marker 또는 Collider 문제로 분류한다. 수정 후 동일 조건의 근접 Grab 실패율이 감소했는지 비교한다.

위 수치는 보고 형식을 설명하기 위한 예시이며 실제 측정값이 아니다. 운영 기준시간, marker 기준 거리와 개선 목표값은 기준 실행 데이터를 수집한 뒤 확정한다.

## 14. 2026-08-24 추가 합의: 과정 이수·개인 진도·재이수 분석

### 14.1 분석 우선순위

대시보드의 최상위 목적은 개별 PPE의 단순 완료율을 나열하는 것이 아니라 다음 질문에 답하는 것이다.

1. 사용자가 선택한 교육과정을 끝까지 이수했는가?
2. 완료하지 못했다면 마지막으로 정상 수행한 단계와 막힌 단계는 어디인가?
3. 메뉴 종료, 앱 백그라운드 전환, 장시간 미입력, 충돌, 연결 종료 또는 전원 종료 추정 중 어떤 경로로 이탈했는가?
4. 같은 사용자가 다시 이수했을 때 완료 여부, 오류, 힌트, 재시도와 수행시간이 어떻게 변했는가?
5. Learning, Training, Test 중 어느 모드가 상대적으로 어려운가?
6. 여러 사용자가 공통으로 멈추거나 이탈하는 잘못 설계된 구간은 어디인가?

이에 따라 최상위 KPI는 다음 순서로 둔다.

| 우선순위 | 지표 | 표시 기준 |
| --- | --- | --- |
| 1 | 전체 과정 이수율 | `course_completed=true`인 수행 회차 / 시작된 수행 회차 |
| 2 | 단계별 도달·완료·이탈 퍼널 | 모드별 필수 checkpoint를 기준으로 시작 수, 도달 수, 완료 수, 이탈 수 표시 |
| 3 | 병목 구간 | 긴 체류시간, 반복 오류, 힌트·재시도와 이탈이 함께 집중되는 단계 |
| 4 | 개인별 진도 | 현재 단계, 마지막 완료 checkpoint, 전체 필수 checkpoint 대비 완료 수 |
| 5 | 재이수 변화 | 동일 사용자의 이전 회차와 최근 회차를 완료·오류·힌트·재시도·시간 축으로 비교 |
| 6 | 모드별 난이도 | 모드별 이수율, 단계 이탈률, 통과 수행시간 중앙값, 오류·힌트·재시도 분포 |

표본이 적을 때는 자동 순위나 단일 점수보다 실제 인원 수와 분자·분모를 함께 표시한다. 소수 사용자의 결과만으로 특정 구간을 결함이라고 확정하지 않고 **설계 검토 후보**로 표시한다.

### 14.2 개인별 프로그레스 모델

개인별 진도는 다음 계층으로 연결한다.

```text
participant
└─ course
   └─ mode
      └─ attempt
         └─ checkpoint / stage event
```

각 수행 이벤트에는 최소한 다음 필드를 포함한다.

```text
participantId / courseId / mode
sessionId / attemptId / attemptNumber
stageId / checkpointId
eventName / outcome / errorCode
timestamp / elapsedFromAttempt / duration
endReason / appVersion
```

개인별 화면에는 다음 정보를 표시한다.

- 선택 과정과 모드별 전체 진도
- 현재 단계와 마지막 정상 완료 checkpoint
- 미완료 세션의 마지막 이벤트와 이탈 원인
- 회차별 과정 완료 여부와 완료 시각
- 회차별 일반 오류, 순서 오류, 치명적 오류, 힌트, 재시도와 수행시간
- 첫 회차, 이전 회차, 최근 회차의 변화
- 반복해서 막힌 단계와 중단 후 재개 여부

진도율은 PPE 개수의 완료 비율이 아니라 해당 모드의 **필수 과정 checkpoint 완료 수 / 필수 과정 checkpoint 전체 수**로 계산한다. 분기 과정은 사용자가 실제로 선택한 유효 경로의 필수 checkpoint만 분모에 포함한다.

사용자 식별에는 실명 대신 동의받은 참여자 코드 또는 익명 UUID를 사용한다. 이름이 필요한 운영 환경에서는 이름과 익명 ID의 매핑을 이벤트 데이터와 분리하고 관리자만 접근하도록 한다.

### 14.3 중도 이탈과 비정상 종료 판정

정상 종료 버튼을 누르지 않고 전원이 꺼지거나 앱이 강제 종료되면 마지막 종료 이벤트를 전송할 수 없다. 따라서 앱은 상태 변화 이벤트와 함께 설정 가능한 주기의 `heartbeat`를 저장하고, 다음 실행 또는 서버 집계 시 미종료 세션을 복구 판정한다.

| `endReason` | 판정 근거 | 해석 |
| --- | --- | --- |
| `completed` | `course_completed` 후 정상 세션 종료 | 과정 이수 |
| `explicit_exit` | 사용자가 메뉴·종료 버튼을 선택 | 명시적 중도 종료 |
| `app_backgrounded` | 앱 pause 또는 focus 상실 후 허용시간 안에 복귀하지 않음 | 홈 이동·앱 전환 가능성 |
| `inactivity_timeout` | 마지막 유효 행동 후 기준시간 초과 | 장시간 정지 또는 이탈 |
| `crash_recovered` | 다음 실행에서 충돌 기록과 미종료 세션이 함께 확인됨 | 앱 충돌 |
| `unexpected_disconnect` | 마지막 heartbeat 이후 종료 이벤트 없이 세션 단절 | 연결·프로세스 종료 추정 |
| `power_off_suspected` | 종료 이벤트가 없고 다음 실행에서 장시간 단절이 확인되며 다른 원인이 없음 | 전원 종료 가능성에 대한 추정값 |
| `unknown` | 근거가 충분하지 않음 | 원인을 임의로 확정하지 않음 |

`power_off_suspected`는 장치 전원 종료를 직접 검출한 사실로 표시하지 않는다. 마지막 checkpoint, 마지막 이벤트 시각, 마지막 heartbeat와 다음 실행 시각을 함께 제공해 **추정 원인**임을 명확히 한다.

### 14.4 수행을 잘했는지 판단하는 기준

초기 버전에서는 모호한 종합 정확도 점수나 임의 가중치 점수를 만들지 않는다. 수행 결과는 다음 네 축을 각각 표시한다.

| 축 | 측정 기준 | 주의사항 |
| --- | --- | --- |
| 이수 | 모든 필수 checkpoint 완료 여부 | 단순 Trigger 입력이 아니라 실제 과정 상태 완료를 기준으로 한다. |
| 안전성 | 치명적 안전 오류 발생 수 | 치명적 오류의 정의는 과정 전문가와 단계별로 확정한다. |
| 절차 정확성 | 일반 오류와 순서 오류 발생 수 | 정상 행동을 처리하는 도메인 로직의 판정 결과에서 기록한다. |
| 자립성 | 힌트 사용과 재시도 횟수 | Learning, Training, Test의 안내 허용 범위를 분리한다. |

수행시간은 위 네 축과 분리한다. 빠른 수행만으로 향상이라고 판단하지 않고, 다음 조건을 만족할 때만 **정확성을 유지하며 시간이 단축됨**으로 표시한다.

```text
courseCompleted = true
criticalErrorCount = 0
sequenceErrorCount <= previousAttempt.sequenceErrorCount
wrongActionCount <= previousAttempt.wrongActionCount
duration < previousAttempt.duration
```

첫 회차에는 비교 대상이 없으므로 `정확성 유지` 또는 `향상`을 판정하지 않고 이수, 안전 오류, 절차 오류, 힌트, 재시도와 수행시간의 기준값만 저장한다. 재이수 향상도는 같은 사용자·같은 과정·같은 모드·같은 앱 업데이트 버전끼리만 비교한다.

### 14.5 단계별 행동 판정 계약

코드로 정확성을 측정하려면 각 단계의 상태 소유자가 정상 행동과 오류를 명시적으로 판정해야 한다. 컨트롤러의 모든 버튼 입력이나 Ray 적중을 오류로 세지 않고, 실제 과정 로직이 행동의 유효성을 확정한 시점에만 분석 이벤트를 기록한다.

각 단계에는 다음 계약을 작성한다.

| 정의 | 의미 | 기록 결과 예시 |
| --- | --- | --- |
| 정상 행동 | 현재 상태에서 요구되는 유효 행동 | `Success` |
| 허용 행동 | 진행에는 영향이 없지만 오류도 아닌 행동 | 기록 제외 또는 `Allowed` |
| 잘못된 행동 | 잘못된 대상·조작을 선택 | `WrongAction` |
| 순서 오류 | 필수 선행 단계 전 다음 행동을 시도 | `SequenceError` |
| 치명적 오류 | 안전상 실패로 처리해야 하는 행동 | `CriticalError` |
| 도움 사용 | 힌트·추가 안내를 요청하거나 자동 도움을 받음 | `HintUsed` |
| 재시도 | 같은 단계의 실패 후 다시 시작 | `Retry` |

구현 흐름은 다음과 같다.

```text
사용자 행동
→ 기존 과정 상태 소유자가 성공·오류·허용을 판정
→ 분석 기록기가 판정 결과와 현재 stage/checkpoint를 이벤트로 저장
→ 로컬 큐 또는 수집 API로 전송
→ 대시보드가 개인 회차와 전체 집계를 계산
```

분석 기록기는 기존 과정의 성공·실패 판정을 새로 대신하지 않고 판정 결과를 관찰한다. 분석 전송 실패가 교육과정 진행을 막아서는 안 되며, 네트워크가 없을 때는 로컬 큐에 보관한 뒤 재전송한다.

### 14.6 모드 난이도와 설계 결함 후보

모드 난이도는 하나의 점수로 고정하지 않고 다음 지표를 함께 비교한다.

- 전체 과정 이수율과 단계별 이탈률
- 통과한 수행의 전체·단계별 시간 중앙값과 P90
- 일반 오류, 순서 오류, 치명적 오류가 발생한 수행 비율
- 힌트 사용자 비율과 사용자당 힌트 횟수
- 재시도가 발생한 수행 비율과 완료까지의 회차 수
- 같은 사용자가 이전 모드에서 다음 모드로 이동했을 때의 변화

잘못 설계된 구간은 다음 신호가 여러 사용자에게 동시에 반복될 때 검토 후보로 표시한다.

1. 해당 단계 도달 후 다음 checkpoint 완료율이 낮다.
2. 이탈 직전 마지막 단계로 자주 기록된다.
3. 통과하더라도 체류시간이 다른 단계보다 길다.
4. 같은 `errorCode`, 힌트 또는 재시도가 집중된다.
5. 재이수 후에도 같은 병목이 충분히 감소하지 않는다.
6. 목표 발견시간, 예상 탐색구역 이탈과 잘못된 대상 상호작용이 같은 단계에 함께 집중된다.

위 조건의 임계값은 임의로 하드코딩하지 않는다. 기준 실행과 초기 사용자 데이터를 확보한 뒤 과정별 분포를 보고 확정한다. 대시보드는 원인 가설과 수정 대상을 제안할 수 있지만, 구간 결함의 최종 판단은 과정 전문가와 콘텐츠 설계자가 한다.

### 14.7 데이터 수집 API와 Meta Horizon 데이터

여기서 요구하는 “Google처럼 데이터를 불러오는 편의”는 외부 플랫폼 화면을 복제하는 것이 아니라, 앱의 수행 이벤트를 한 번 수집한 뒤 웹 대시보드가 기간·사용자·과정·모드·회차별로 자동 조회하는 구조를 뜻한다.

```text
Unity 앱
→ 이벤트 수집 API
→ 원시 이벤트 저장소
→ 집계 API
→ 관리자 종합 분석 / 개인별 프로그레스 대시보드
```

필요한 API 역할은 다음과 같다.

- 이벤트 단건·일괄 수집과 오프라인 재전송 중복 제거
- 사용자별 현재 진도와 수행 회차 조회
- 과정 퍼널, 병목 단계와 이탈 원인 집계
- 동일 사용자의 회차별 변화 조회
- 모드별 난이도 비교
- 앱 업데이트 버전 필터

Meta Horizon Developer Dashboard는 입점 후 플랫폼 노출·설치·활성 사용자·성능 등을 확인하는 외부 자료로 분리한다. 2026-08-24 공식 문서 확인 기준으로 일반적인 외부 실시간 Analytics API는 문서화되어 있지 않고, 과거 CSV 다운로드도 출시일과 활성 사용자 수 등의 조건이 있다. 따라서 100명 미만의 소규모 평가에서도 작동해야 하는 과정 이수·이탈·재이수 분석은 Meta 데이터에 의존하지 않고 프로젝트 자체 수집 API를 기준으로 한다.

- Meta Analytics 개요: `https://developers.meta.com/horizon/resources/publish-monitor/`
- Meta 과거 데이터 다운로드 조건: `https://developers.meta.com/horizon/resources/analytics-data-download/`

Meta가 이후 공식 Analytics API 또는 적용 가능한 내보내기 기능을 제공하면 외부 데이터 adapter로 추가한다. Meta 로그인 화면 자동화, 비공개 endpoint 호출이나 화면 scraping은 인증·보안·화면 변경 위험 때문에 구현 기준에서 제외한다.

### 14.8 구현 전 확정해야 할 항목

실제 계측 코드를 작성하기 전에 다음 항목을 과정·모드별 표로 확정한다.

1. 과정별 필수 checkpoint와 선택 분기
2. 각 checkpoint의 정상 행동, 허용 행동, 일반 오류, 순서 오류와 치명적 오류
3. 모드별 허용 안내와 힌트 정의
4. 수행 회차 시작·완료·중단·재개 조건
5. inactivity와 비정상 종료를 추론할 기준시간 및 heartbeat 주기
6. 앱 업데이트로 과정 로직이 달라졌을 때 재이수 비교 가능 여부
7. 사용자 동의, 익명 ID 발급, 보관기간과 삭제 정책
8. checkpoint별 `discoveryStartEvent`, 정상 목표, 시작 기준 Pose와 예상 yaw·pitch 탐색구역
9. 지원 장치별 `trackingSource`, eye tracking 권한·보정 여부와 원시 궤적 저장 범위

위 계약이 없으면 코드가 수집한 입력 횟수만으로 정확성이나 학습 향상을 판단하지 않는다.

## 15. 2026-08-25 과정 중심 대시보드 V2 목업

### 15.1 생성 파일과 보존 범위

- 현재 목업: `server/public/dashboard/index.html`
- 기존 목업: `output/html/PPE_Training_Dashboard.html`을 비교 기준으로 보존했다.
- V2는 외부 라이브러리 없이 동작하는 단일 HTML이며 실제 수집 API 연결 전 구조 검증용 모의 데이터를 사용한다.
- 기존 목업의 `accuracy >= 70` 기반 통과 판정을 V2에 가져오지 않았다. 과정 완료 여부는 수행 상태 `status=completed`와 마지막 필수 checkpoint 완료로 독립 관리한다.

### 15.2 화면 정보구조

V2의 전역 화면은 다음 순서로 구성했다.

1. 전체 개요: 시작된 과정, 전체 과정 이수율, 미완료·중도 이탈, 재이수 개선 쌍, 과정 퍼널
2. 과정 병목·이탈: checkpoint별 도달·완료·단계 이탈·체류시간과 종료 원인
3. 재이수·모드 난이도: 같은 참여자·모드·앱 업데이트 버전의 연속 회차 비교와 모드별 지표 분리
4. 업데이트 영향: 앱 버전별 이수율·이탈률·완료시간·오류·힌트·재시도, 모드별 차이, checkpoint 병목 변화와 동일 참여자의 버전 전후 비교
5. 개인 프로그레스: 최근 checkpoint 진도, 중단·재개, 회차별 오류·힌트·재시도·시간
6. UX 설계 신호: 발견성, 예상 탐색구역 이탈, 목표 노출 후 미상호작용, 상호작용·피드백 신호
7. 데이터 연동: Unity 이벤트 수집 API, 원시 이벤트, 집계 API와 Meta Horizon 데이터의 분리

PPE별 헬멧·장갑·마스크 완료율은 최상위 탐색 축에서 제거했다. 장비별 수치가 필요할 때는 checkpoint·오류 또는 이름 기반 작업구역의 원인을 좁히는 하위 진단으로 추가한다.

### 15.3 모의 데이터와 계산 계약

현재 V2 모의 데이터는 익명 참여자 8명, 수행 17회, 필수 checkpoint 7개로 구성했다. 완료 수행은 10회이고, 같은 참여자·모드·앱 업데이트 버전으로 비교 가능한 재이수 쌍은 5개다. 업데이트 전후 비교용으로 같은 참여자·같은 모드에서 `0.0.9 → 0.1.0` 기록을 가진 비교 쌍 4개를 포함한다.

재이수 개선은 다음 조건으로 계산한다.

```text
현재 회차가 과정 완료
AND 치명적 오류 0회
AND 순서 오류가 이전보다 증가하지 않음
AND 일반 오류가 이전보다 증가하지 않음
AND 완료·오류·힌트·재시도 중 하나 이상 개선
```

수행시간 단축은 위 정확성 유지 조건을 만족할 때만 `안전한 시간 단축`으로 별도 표시한다. 개인·모드·병목 화면은 종합 정확도 점수를 만들지 않고 완료, 치명적 오류, 순서 오류, 일반 오류, 힌트, 재시도와 시간을 각각 보여 준다.

중도 이탈은 직접 기록과 추정을 구분한다. `explicit_exit`, `app_backgrounded`, `inactivity_timeout`은 직접 상태 기록으로 표시하고, `power_off_suspected`, `unexpected_disconnect`, `unknown`은 추정 배지와 함께 표시한다.

### 15.4 필터와 내보내기

전역 필터는 기간, 참여자, 수행 모드와 앱 업데이트 버전으로 구성했다. 개인 프로그레스도 전역 기간·모드·앱 버전 필터를 따르며, 필터에 해당하는 수행이 없을 때는 빈 상태를 표시한다.

`앱 업데이트 버전`은 교육과정 개정판을 뜻하지 않는다. Unity 프로젝트의 현재 `bundleVersion`은 `0.1.0`, Android `bundleVersionCode`는 `1`이다. V2 모의 데이터는 이전 앱 상태를 `0.0.9`, 현재 상태를 `0.1.0`으로 구분한다. 개인 학습 향상 비교는 같은 앱 버전 안에서 수행하고, 앱 업데이트 영향은 별도의 화면에서 버전 간 집계와 동일 참여자·동일 모드 비교로 분석한다.

업데이트 영향 화면에서는 버전 선택 필터를 자동으로 전체로 두어 두 버전이 동시에 비교되게 한다. 기간·참여자·모드 필터는 그대로 적용하므로 특정 기간, 사용자 또는 모드 안에서 업데이트 전후 차이를 좁혀 볼 수 있다.

업데이트 영향 화면의 사용자용 문구는 분석 용어보다 질문 형태를 우선한다. 핵심 질문은 `업데이트 후 더 많은 사람이 끝까지 했는가`, `중간에 멈춘 사람이 줄었는가`, `실수와 재시도가 줄었는가`, `특정 단계에서 덜 막혔는가`의 네 가지다. 화면의 `표본`, `중앙값`, `회귀`, `checkpoint 병목` 같은 표현은 각각 `기록 수`, `대표값`, `나빠짐`, `어느 단계에서 더 막혔는가`처럼 풀어서 표시한다.

대시보드의 모든 명시적 CSS 글자 크기는 최소 `12px`로 맞춘다. 배지, 표 제목, 보조 설명, 모바일 비교표와 하단 안내도 예외로 두지 않는다.

`현재 범위 CSV`는 현재 필터에 포함된 수행 회차 요약을 UTF-8 CSV로 내보내는 목업 기능이다. 실제 API 연결 후에는 동일한 필터 계약을 집계 API 요청과 서버 내보내기에 재사용한다.

### 15.5 앱 업데이트 영향 판정 기준

업데이트에 따라 이수 난이도가 변했는지는 단일 종합 점수로 판정하지 않는다. 다음 지표를 이전 버전과 현재 버전으로 나누어 각각 비교한다.

- 전체 과정 이수율과 중도 이탈률
- 완료 수행시간 중앙값
- 순서 오류와 일반 오류의 합계 중앙값
- 힌트와 재시도 중앙값
- checkpoint별 도달 수행 대비 단계 이탈률과 체류시간 중앙값
- 같은 참여자·같은 모드의 버전 전후 이수 여부, 오류, 재시도와 수행시간

이수율 상승, 이탈 감소, 오류·재시도 감소와 완료시간 단축이 같은 방향으로 반복되면 `난이도 완화 후보`로 본다. 반대로 이수율 하락, 이탈 증가, 오류·재시도 증가와 특정 checkpoint 체류 증가가 반복되면 `회귀 후보`로 본다. 지표가 서로 반대 방향이면 `혼합·표본 확인`으로 남긴다.

버전별 참여자 수와 수행 수를 항상 함께 표시한다. 모드 구성이 다른 두 버전의 전체 평균은 직접 비교하지 않고 Learning, Training, Test로 나눈 결과를 우선 확인한다. 같은 참여자의 버전 전후 비교도 재이수에 따른 숙련 효과가 섞일 수 있으므로 업데이트의 인과 효과를 자동 확정하지 않는다. 실제 판단에는 충분한 표본, 동일하거나 유사한 참여자군, 같은 모드·기기 조건과 업데이트 외 변경사항 기록이 필요하다.

### 15.7 아직 필요한 검증과 구현

- 데스크톱·태블릿·모바일 브라우저에서 레이아웃과 모든 화면 전환을 수동 확인한다.
- 기간·참여자·모드·앱 업데이트 버전 필터 조합과 개인 프로그레스 동기화를 브라우저에서 확인한다.
- 업데이트 영향 화면에서 버전별 표, 모드별 비교, 동일 참여자 비교와 checkpoint 변화가 필터에 맞게 갱신되는지 브라우저에서 확인한다.
- CSV 다운로드 파일명·한글·필드값을 실제 다운로드로 확인한다.
- Unity의 실제 상태 소유자에서 checkpoint, 오류, heartbeat와 종료 이벤트를 발생시키는 계측 코드는 아직 구현하지 않았다.
- 이벤트 수집 API, 저장소와 집계 API는 아직 연결하지 않았다.
- UX 예상 탐색구역과 종료 추론 기준시간은 기준 실행 데이터를 수집한 뒤 확정한다.
- Meta Horizon 플랫폼 데이터는 외부 자료로 분리했으며 V2에는 라이브 연결하지 않았다.

### 15.8 Unity 프로젝트에서 실제 수집할 수 있는가

결론은 **대시보드의 핵심 내용 대부분을 Unity에서 수집할 수 있지만, 현재 프로젝트가 이미 수집하고 있는 것은 아니다.** 현재 V2 HTML은 화면과 계산 방식을 확인하기 위한 모의 데이터를 사용한다. `Assets/Scripts`와 `Assets/Editor`의 프로젝트 소유 코드에는 대시보드용 수행 이벤트를 기록·전송하는 계측 코드가 아직 없고, 수집 API·저장소·집계 API도 연결되지 않았다.

#### Unity에서 직접 기록할 수 있는 값

- `Application.version`을 이용한 앱 업데이트 버전
- 익명 처리한 참여자 ID, 수행 회차 ID와 실행 세션 ID
- Learning, Training, Test 중 실행한 모드
- 과정 시작, 각 단계 진입, 단계 완료와 전체 과정 완료
- 단계별 시작시각, 종료시각과 머문 시간
- 순서 오류, 잘못된 행동, 힌트 요청과 재시도 횟수
- 사용자가 누른 명시적 종료, 앱 일시정지·백그라운드 전환과 정상 종료 이벤트
- 중단된 회차를 다시 시작하거나 이어서 수행했는지 여부

#### 기록을 모은 뒤 대시보드에서 계산하는 값

- 끝까지 완료한 사람의 비율
- 중간에 멈춘 사람의 비율과 마지막으로 도달한 단계
- 사람들이 오래 머물거나 자주 그만두는 단계
- 모드별 완료율, 실수, 힌트, 재시도와 수행시간 차이
- 같은 사람이 다시 수행했을 때 나아졌는지 여부
- 앱 업데이트 전후 완료율, 중간 종료, 실수, 재시도와 막히는 단계의 변화

따라서 `이수율`이나 `업데이트 후 난이도 변화`를 Unity가 한 번에 직접 알려 주는 것은 아니다. Unity가 회차별 사실을 기록하고, 대시보드가 여러 기록을 모아 비율과 변화를 계산한다.

#### 정확히 기록하기 어렵거나 별도 자료가 필요한 값

- 기기 전원 종료, 앱 강제 종료 또는 충돌 직전에는 마지막 이벤트를 전송하지 못할 수 있다. 이 경우 마지막 heartbeat 이후 기록이 끊긴 사실을 이용해 `비정상 종료 추정`으로만 표시하며, 전원이 꺼졌다고 확정하지 않는다.
- 일반 Quest의 HMD 방향은 기록할 수 있지만 사용자의 실제 눈동자 시선과 동일하지 않다. 눈동자 시선은 지원 기기, 권한과 별도 Eye Tracking API가 있어야 한다.
- Meta Horizon의 스토어 노출, 설치, 활성 사용자 같은 플랫폼 수치는 Unity 과정 이벤트가 아니다. Meta 측 자료로 별도 관리하고 과정 완료·오류 데이터와 섞지 않는다.

#### 실제 운영을 위해 필요한 구성

```text
Unity 수행 이벤트 기록
→ 기기 내부 임시 저장
→ 네트워크 연결 시 수집 API로 전송
→ 데이터베이스에 회차별 기록 보관
→ 집계 API가 완료율·중간 종료·막힌 단계·버전 차이를 계산
→ 대시보드가 결과를 불러와 표시
```

Quest가 일시적으로 오프라인이어도 기록이 사라지지 않도록 기기 내부에 먼저 저장하고, 연결이 복구되면 다시 전송해야 한다. 개인정보는 직접 이름 대신 익명 참여자 ID를 사용하고, 수집 목적·보관 기간·삭제 기준을 실제 배포 전에 정해야 한다.

### 15.9 2026-08-26 V3 표현·시각화 정리

`server/public/dashboard/index.html`을 V3로 갱신했다. 이번 변경은 기능을 늘리는 작업보다 처음 보는 운영자가 화면의 의미를 바로 이해하도록 용어와 시각화 근거를 정리하는 데 초점을 두었다.

#### 사용자용 용어 변경

- `재이수 개선 쌍`은 `연속 회차 개선` 또는 `연속 회차 비교 N건`으로 바꿨다.
- 개별 비교는 `1→2회차`, `2→3회차`처럼 어느 회차를 비교하는지 직접 표시한다.
- `재이수·모드 난이도`는 `회차·모드 비교`, `과정 병목·이탈`은 `과정 단계·중단`, `개인 프로그레스`는 `사용자별 기록`, `UX 설계 신호`는 `사용성 검토`, `데이터 연동`은 `데이터 상태`로 바꿨다.
- 사용자 화면에서는 `participant`, `checkpoint`, `쌍`과 같은 구현·분석 용어 대신 `사용자`, `과정 단계`, `건`을 사용한다. 코드 식별자와 CSV 필드처럼 데이터 계약에 필요한 내부 이름은 유지할 수 있다.
- HTML이 생성하는 파일은 Meta 제공 CSV와 혼동하지 않도록 `목업 CSV 내려받기`라고 명시한다.

#### 차트 선택 원칙

차트는 화면을 채우기 위한 장식이 아니라 분모, 축, 비교 대상과 판단 질문이 분명할 때만 사용한다.

- 단계별 도달 막대는 `도달 회차 / 시작 회차`라는 동일 분모로 과정 진행 감소를 비교할 수 있으므로 유지한다.
- 모드별 결과와 연속 회차 변화는 완료 여부, 오류, 힌트, 재시도와 시간이 서로 다른 단위이므로 임의의 종합 막대나 단일 점수로 합치지 않고 수치·회차 목록으로 표시한다.
- 데이터 필드 존재 여부를 길이 100% 막대로 표현하던 `필수 이벤트 계약` 시각화는 제거했다. 길이가 수량·비율·변화를 나타내지 않아 판단을 흐렸기 때문이다.
- Meta 플랫폼 정보의 자체 비율 막대도 제거했다. 프로젝트가 Meta의 설치·활성 사용자 지표를 자동 수집하고 있지 않으므로 우리 과정 데이터처럼 보이게 만들지 않는다.
- 차트가 아닌 표가 더 적합한 경우 실제 상태, 수집할 내용과 남은 작업을 행 단위로 표시한다.

#### 데이터 상태와 Meta Horizon 분리

데이터 상태 화면은 다음 여섯 범주의 준비 상태를 `부분 구현`, `목업만`, `설계 확정`으로 구분한다.

1. 사용자 식별
2. 수행 회차
3. 과정·행동
4. 신규·기존 판정
5. 종료·시간
6. 오프라인 동기화

Meta Horizon의 스토어 노출·설치·활성 사용자·플랫폼 성능은 우리 교육 수행 이벤트와 분리된 외부 운영 정보다. 따라서 V3에는 Meta 수치를 흉내 낸 차트 대신 앱의 Meta Horizon Developer Dashboard Analytics 주소로 이동하는 카드형 링크를 제공한다. 현재 우리 대시보드와 자동 연동되지 않는다는 점과 신규 앱이 레거시 CSV 대상이 아니라는 점을 카드 안에 함께 표시한다.

#### 완료한 검증

- `server`의 자동 테스트 9개 통과
- HTML 인라인 JavaScript 문법 확인 완료
- `modeDifficulty`, `repeatPairs`, `dataContractTable` 필수 출력 대상 확인
- 로컬 Express 서버에서 전체 개요, 회차·모드 비교와 데이터 상태 화면 전환 확인
- 사용자 `P-008` 필터에서 `연속 회차 비교 2건`, `1→2회차`, `2→3회차` 표시 확인
- 데이터 준비 상태 표와 Meta 대시보드 카드 링크의 표시·주소·새 탭 속성 확인
- 브라우저 콘솔 경고·오류 없음

아직 실제 수행 이벤트 수집, Unity-서버 연결, MySQL 실데이터 집계와 Meta Analytics 자동 연동은 구현되지 않았다. V3 수치는 계속 구조 검증용 모의 데이터이며 실제 교육 결과로 해석하지 않는다.

### 15.10 2026-08-26 V4 시도 폐기와 V3 기준 복원

V3의 운영자 UX를 개선하기 위해 메뉴를 세 화면으로 축소하고 필터를 접으며 결론 카드를 추가한 V4를 시도했다. 실제 화면 비교 결과 V4는 필요한 분석 화면을 숨기고, 필터 조작 단계를 늘리며, 기존 검토 후보와 중복되는 큰 카드를 추가해 V3보다 정보 탐색성이 낮아졌다. 카드와 여백도 과도하게 커져 화면이 불필요하게 길어졌다.

따라서 V4는 기준 버전으로 사용하지 않고 폐기했다. `server/public/dashboard/index.html`은 V3의 다음 구조를 복원했다.

- 7개 분석 화면과 데스크톱·모바일 탐색 메뉴
- 항상 보이는 기간·사용자·수행 모드·앱 업데이트 버전 필터
- 시작된 과정, 전체 과정 이수율, 미완료·중도 이탈과 연속 회차 개선의 4개 KPI
- 단계별 도달 현황, 우선 검토 후보와 모드별 과정 결과의 기존 배치

사용자가 직접 지적한 두 레이아웃 문제만 V3에 제한적으로 반영했다.

1. `작업구역별 문제 신호`는 좁은 한 줄 안에 구역명, 체류시간과 상대 막대를 붙여 넣던 표현을 제거했다. 구역별 독립 카드에 문제 신호 건수, 도달 회차와 대표 체류시간을 분리해 배치하고, 화면 폭에 따라 두 열 또는 한 열로 표시한다.
2. Meta Horizon 링크 카드는 `height: 100%`를 사용하지 않는다. 데이터 열에 `align-items: start`를 적용하고 링크와 내부 카드에 최대 너비를 제한해 부모 섹션과 푸터를 침범하지 않도록 했다.

V4에서 추가했던 `지금 먼저 확인` 카드, 접힌 필터, 세 개 메뉴 구조와 확대된 전역 여백은 모두 제거했다. 이후 대시보드 개선도 기존 정보구조를 먼저 보존하고 사용자가 지목한 문제를 한 번에 하나씩 수정한다.

복원 후 Express 자동 테스트 10개와 HTML 인라인 JavaScript 문법 검사를 통과했다. 로컬 브라우저에서 V3의 7개 메뉴와 항상 보이는 필터를 확인했고, `사용성 검토`의 작업구역 카드가 겹치지 않는 것과 `데이터 상태`의 Meta 카드·링크·푸터가 각 부모 경계 안에 유지되는 것을 확인했다. 브라우저 콘솔 경고·오류는 없었다.

#### 대시보드 버전과 Unity 앱 버전의 구분

대시보드 `V2`, `V3`, 폐기된 `V4`는 웹 화면과 정보구조의 개정 번호다. 모의 데이터에 포함된 `v0.0.9`, `v0.1.0`은 Unity 앱의 `Application.version` 또는 `bundleVersion`을 뜻하며 대시보드 버전과 관계가 없다.

| 종류 | 예시 | 사용 목적 |
|---|---|---|
| 대시보드 화면 버전 | V2, V3, 폐기된 V4 | 메뉴, 용어, 카드와 차트 등 웹 UI 변경 이력 구분 |

현재 모의 데이터는 Unity 앱 `v0.0.9 → v0.1.0` 변화를 설명하기 위한 예시다. 실제 업데이트 효과로 해석하지 않으며, 실제 수행 이벤트와 충분한 표본이 수집된 뒤 같은 모드·기기·과정 조건을 확인해 판단한다.

- 차트는 분모, 축, 비교 대상과 판단 질문이 명확할 때만 사용한다.
- 레이아웃 결함은 문제가 발생한 카드와 반응형 구간만 제한적으로 수정한다.
- 실제 API 연결 전까지 모든 수치는 모의 데이터임을 화면과 문서에 계속 표시한다.

## 16. 2026-08-25 Meta 사용자 식별과 컨트롤러 안내 UX 합의

### 16.1 결정 배경과 이번 합의의 범위

대시보드가 개인의 반복 수행과 재이수 변화를 연결하려면 앱 재실행 뒤에도 같은 사용자를 식별할 기준이 필요하다. Quest 배포 환경에서는 Meta Horizon 계정으로 사용자를 식별하고, Unity Editor·PC OpenXR·인증 실패 환경에서는 일반 사용자 모드를 유지한다.

근본 원인은 현재 최초 키보드의 `NameInput`이 이름 입력, 진행 게이트, A 버튼 상세 교육 진입과 교육 완료 후 복귀를 함께 소유하지만, 향후 사용자 식별은 Meta 계정과 내부 사용자 ID가 담당하게 된다는 점이다. 키보드 표시만 제거하거나 Meta 계정 존재만으로 가이드를 생략하면 진행 중단 또는 미완료 사용자의 안내 누락이 생길 수 있다.

이번 문서에는 사용자 식별, 사용자 테이블, 최초 진입 흐름과 컨트롤러 안내 UX의 합의 내용을 추가했다. 2026-08-25 현재 Meta Platform SDK와 Express 서버가 설치됐고 users/external identities CRUD 모듈과 migration이 구현됐다. 실제 MySQL 연결, Meta 사용자 증명 검증, Unity 인증 코드와 가이드 생략 코드는 아직 적용하지 않았다.

### 16.2 Meta SDK 모드와 일반 모드

Meta Platform SDK 패키지는 프로젝트에 설치한 상태로 유지하되, 런타임 설정에 따라 SDK 초기화 호출 여부를 결정한다. 패키지를 설치·제거하는 방식으로 모드를 전환하지 않는다.

```text
Identity Mode
├─ Auto
│  ├─ Quest에서 Meta 인증 성공 → Meta
│  └─ Editor·PC OpenXR·인증 실패 → Local/Guest
├─ Meta
└─ Local/Guest
```

설정 모드, 현재 인증 상태와 현재 훈련 세션은 서로 다른 상태로 관리한다.

- 설정 모드: `Auto`, `Meta`, `Local/Guest`
- 인증 상태: 초기화 중, 인증됨, 오프라인, 실패
- 훈련 세션: 내부 사용자 ID, attempt ID, 가이드 완료 버전과 전송 대기 이벤트

USB 분리나 Quest Link 재연결로 Meta SDK 세션 또는 Play Mode가 다시 초기화되어도 직렬화된 Identity Mode까지 자동 변경하지 않는다. 훈련 attempt가 시작된 뒤에는 연결 상태 변화만으로 사용자를 Meta와 Local 사이에서 교체하지 않는다. 연결이 끊기면 같은 attempt의 이벤트를 기기 로컬 큐에 보관하고, 재인증으로 같은 사용자가 확인된 뒤 전송을 재개한다.

Meta 인증 실패 또는 사용자 불명 상태에서 가이드를 임의로 생략하지 않는다. 계정을 확인하지 못한 경우에는 가이드를 표시하는 방향으로 실패 안전성을 유지한다.

### 16.3 사용자 테이블과 후속 데이터 레코드

초기 구현은 사용자 인식과 사용자 CRUD부터 시작한다. 훈련 attempt와 원시 이벤트는 사용자 식별이 안정된 뒤 관계 테이블로 추가한다.

```text
users
└─ external_identities
   └─ users의 외부 인증 연결

users
└─ attempts
   └─ attempt_events
```

`users`는 앱 내부 UUID를 기본키로 사용한다. Meta 표시 이름이나 변경 가능한 별칭을 기본키로 사용하지 않는다. Meta SDK가 반환하는 사용자 식별값은 `external_identities`에 `provider=meta`와 함께 보관하고, 서버 검증 뒤 내부 사용자와 연결한다. 표시 이름이 운영상 필요하면 인증 식별자와 분리된 관리자용 별칭으로 관리한다.

초기 사용자 필드는 다음을 기준으로 한다.

- 내부 사용자 UUID
- 익명 참여자 코드
- 상태: active/inactive 또는 soft-delete 상태
- 인증 provider와 provider user ID
- 최초 생성시각, 최근 접속시각
- `controllerGuideVersionCompleted`
- 필요 시 참고용 `playCount`

사용자에게 훈련 기록이 연결된 뒤에는 사용자를 물리 삭제해 외래키 관계를 끊지 않는다. 일반 삭제 요청은 상태 또는 삭제시각을 기록하는 soft delete를 우선한다.

후속 구현에서 `attempts`에는 사용자 ID, 모드, 앱 버전, 시작·완료 상태와 시간을 기록하고, `attempt_events`에는 checkpoint, 오류, 힌트, 재시도와 종료 근거를 누적한다. 사용자 테이블에 수행 결과 필드를 계속 추가하지 않는다.

#### 16.3.1 2026-08-25 사용자 CRUD 모듈 구현 상태

서버에 다음 구조를 구현했다.

- `users`: 내부 UUID, 익명 참여자 코드, 상태, 컨트롤러 가이드 완료 버전, 참고용 play count와 생성·최근접속·수정·삭제시각
- `external_identities`: 내부 사용자 UUID, `provider=meta`, 앱 범위 Meta 사용자 ID, 사용자 연령대와 검증시각
- Meta 사용자 ID는 생성 후 일반 수정 API에서 바꾸지 않는다.
- 이름, Horizon 사용자명, 프로필 사진과 정확한 생년월일 필드는 받지 않는다.
- `DELETE`는 외래키 관계를 보존하도록 `status=deleted`, `deleted_at`을 기록하는 soft delete다.
- 목록 응답은 외부 사용자 ID를 일괄 노출하지 않고 단일 사용자 조회에서만 identity를 포함한다.

구현 API는 다음과 같다.

```text
POST   /api/users
GET    /api/users?limit=20&offset=0
GET    /api/users/:userId
PATCH  /api/users/:userId
DELETE /api/users/:userId
```

지원하는 생성 입력은 `metaUserId`, `ageGroup`, `controllerGuideVersionCompleted`이며, 수정 입력은 `status`, `ageGroup`, `controllerGuideVersionCompleted`로 제한한다. 훈련 결과 필드는 이 CRUD에 추가하지 않는다.

MySQL migration은 `users`, `external_identities`, `schema_migrations`를 구성하고 `npm run db:migrate`로 실행한다. 이 PC에는 Bitnami WAMP의 MariaDB `10.4.25` 서비스가 `127.0.0.1:3306`에서 실행 중이지만 프로젝트용 DB·계정·비밀번호는 확인되지 않았다. 기존 DB를 임의로 변경하지 않기 위해 migration과 mysql2 쿼리는 실제 DB에서 실행하지 않았다.

Meta 증명 검증 미들웨어가 없으므로 개발 환경에서만 `ENABLE_UNAUTHENTICATED_USER_CRUD=true`를 사용한다. PM2 운영 환경에서는 기본적으로 CRUD 라우트를 비활성화하며 Meta 인증이 연결되기 전에는 외부에 공개하지 않는다.

메모리 저장소를 사용한 자동 테스트에서 생성, 단일 조회, 목록, 수정, soft delete, 중복 Meta ID 충돌, 입력 제한, 잘못된 JSON과 운영 비활성화 플래그를 검증했다. 이는 MySQL 실연결 또는 Meta 계정 인증 성공을 의미하지 않는다.

### 16.4 최초 키보드 단계 제거와 향후 기업 로그인

Meta 계정 또는 Local/Guest 식별을 사용하므로 현재 최초 진입에서 이름을 직접 입력받는 키보드 단계는 제거한다. 키보드 에셋과 한글 입력 코드는 삭제하지 않고 향후 기업 로그인 기능에 재사용할 수 있도록 보존한다.

키보드 프레젠테이션 오브젝트만 숨기는 것으로 완료하지 않는다. 현재 `PPEVoiceFlowDirector`의 `NameInput`, `NotifyNameSubmitted()`와 컨트롤러 교육 복귀 경로가 진행 게이트를 소유하므로, 인증 완료 상태가 기존 이름 제출 게이트를 대체해야 한다.

목표 흐름은 다음과 같다.

```text
앱 시작
→ Meta 또는 Local/Guest 사용자 식별
→ 내부 사용자 조회 또는 생성
→ 최초 컨트롤러 안내와 상세 교육 분기
→ CardIntro
```

향후 기업 로그인을 추가할 때는 사용자 식별 provider를 `enterprise`로 확장하고, 이후 컨트롤러 안내와 훈련 흐름은 같은 내부 사용자 ID를 사용한다.

### 16.5 컨트롤러 안내의 음성 불변조건

사용자가 어떤 컨트롤러 교육 경로를 선택하더라도 다음 두 기능을 최초 교육에서 음성으로 알게 한다.

1. 오른쪽 A 버튼으로 상세 컨트롤러 교육을 요청할 수 있다.
2. 훈련 중 스틱 클릭으로 미니 컨트롤러 가이드를 표시하거나 숨길 수 있다.

별도의 `GuideChoice` 화면이나 미니 가이드 내부의 새 버튼을 추가하지 않는다. 기존 최초 간단 컨트롤러 안내 음성에 A 버튼을 통한 상세 교육 진입을 안내하고, 상세 교육 음성에도 미니 가이드 호출 방법이 전달되도록 음성 계약을 유지한다.

```text
최초 간단 컨트롤러 안내
→ A 버튼과 상세 교육 진입 방법 안내
→ A 입력 시 상세 컨트롤러 교육
→ 입력하지 않으면 기존 다음 단계

상세 컨트롤러 교육
→ 기존 상세 단계 수행
→ 스틱 클릭 미니 가이드 On/Off 방법 안내
→ 다음 단계
```

A 버튼을 PPE 훈련 전체 구간의 전역 교육 토글로 사용하지 않는다. 상세 교육은 음성, 프레젠테이션과 상태 전이를 함께 소유하므로 안전한 최초 안내 구간에서만 분기한다. 훈련 진행 중에는 기존 스틱 클릭 미니 가이드가 보조 역할을 담당한다.

현재 코드에서 오른쪽 A는 `PPEVoiceFlowDirector`의 `primaryButton`/`buttonSouth` 입력으로 상세 교육 요청에 연결되어 있고, 요청은 `NameInput` 상태에서만 허용된다. 미니 가이드는 `ControllerGuideMiniActivator`가 좌·우 스틱 클릭으로 On/Off한다. 키보드 제거 시 A 입력의 허용 상태를 새 인증 완료 이후의 최초 간단 안내 구간으로 옮기되, 기존 미니 가이드 입력 소유권은 보존한다.

### 16.6 신규·기존 사용자와 가이드 생략 기준

신규·기존 사용자 분류는 다음 두 단계 우선순위로 확정한다. 1순위는 앱 범위 Meta 사용자 ID를 통한 계정 식별이고, 2순위는 그 계정에 연결된 실제 시나리오 완료 기록이다. 서버가 가동 중이면 서버 완료 기록을 우선 조회하고, 서버 미구축·오프라인 상태에서는 같은 Meta ID별 로컬 완료 기록을 사용한다. 서버와 로컬 중 어느 한쪽에 완료된 시나리오가 1개 이상 있으면 기존 사용자로 `Welcome_Old`를 적용하고, 모두 0개면 신규 사용자로 `Welcome_New`를 적용한다. New 음원 재생 완료와 앱 실행 횟수는 기존 사용자 판정 근거가 아니다. 로컬 기록은 실제 완료 이벤트를 오프라인 큐로 저장하고 서버 연결 후 중복 없이 동기화한다.

Meta 계정이 존재하거나 한 번 앱을 실행했다는 사실만으로 컨트롤러 교육 완료를 판정하지 않는다. 사용자가 A 버튼과 미니 가이드 안내를 포함한 필수 음성 지점까지 실제로 완료했을 때만 서버에 현재 가이드 버전을 기록한다.

```text
controllerGuideVersionCompleted < currentControllerGuideVersion
→ 최초 안내 또는 필요한 교육 실행

controllerGuideVersionCompleted >= currentControllerGuideVersion
→ 자동 교육 생략 가능
```

가이드 내용이나 입력 체계가 바뀌면 `currentControllerGuideVersion`을 올려 기존 사용자에게도 새 안내를 다시 제공할 수 있다. 안내 음성이 끝나기 전에 앱을 종료한 사용자는 플레이 횟수가 1 이상이어도 완료 사용자로 처리하지 않는다.

1차 SDK·사용자 식별 구현에서는 가이드 생략 기능을 켜지 않는다. 직렬화된 `EnableReturningUserGuideSkip` 기능 플래그의 기본값을 `false`로 두고, Meta 사용자 조회, 서버 사용자 연결과 가이드 완료 저장이 검증된 뒤 별도 변경으로 활성화한다. 주석 처리된 비활성 코드를 기준으로 삼지 않고 컴파일되는 기능 플래그 경로로 관리한다.

### 16.7 구현 순서

1. 대시보드의 사용자·수행·이벤트 데이터 계약을 확정한다.
2. Unity의 실제 상태 소유자에서 수집할 수 있는 값과 이벤트 발생 시점을 확정한다.
3. Meta Platform SDK와 App ID·테스트 사용자 설정을 독립 테스트 범위에서 검증한다.
4. `IUserIdentityProvider` 아래에 Meta와 Local/Guest 구현을 분리한다.
5. Express와 DB에 사용자 조회·생성·수정·soft delete 및 외부 인증 연결을 구현한다.
6. Unity 인증 결과를 서버에서 검증하고 내부 사용자 UUID를 발급한다.
7. 이름 입력 게이트를 인증 완료 게이트로 교체하고 최초 간단 안내의 A 분기를 연결한다.
8. 상세 안내 완료 지점에서 가이드 완료 버전을 기록한다.
9. Link 재연결·오프라인에서도 같은 사용자와 attempt가 유지되는지 확인한다.
10. 검증 뒤 `EnableReturningUserGuideSkip`을 활성화한다.
11. 이후 `attempts`, `attempt_events`, 집계 API와 대시보드 실데이터 조회를 추가한다.

- 입력: 오른쪽 A 상세 교육 분기와 스틱 클릭 미니 가이드
- UI: 최초 키보드 프레젠테이션 비표시, 향후 기업 로그인 재사용
- 서버: Express 사용자 CRUD, Meta 인증 검증과 내부 사용자 upsert
- 데이터베이스: users, external identities, 이후 attempts와 events

## 17. 2026-08-26 실제 훈련 데이터 계약 및 대시보드 측정 기준

### 17.1 데이터 연결의 기본 원칙

대시보드의 모든 값은 다음 관계를 따라야 한다.

```text
사용자
└ 세션
  └ 교육 모드
    └ 시나리오
      └ 단계
        └ PPE 개별 항목
          └ 입력·검사·선택·음성 이벤트
            └ 결과 및 시간
```

임의의 사용자 번호, PPE 이름, 단계명, 경고 수치를 목업 데이터로 추가하지 않는다. 경고나 요약 지표를 표시할 때는 반드시 원본 이벤트와 계산 규칙을 함께 확인할 수 있어야 한다.

### 17.2 현재 Unity에서 실제로 수집 가능한 데이터

`PPETrainingTelemetryCapture`가 세션 JSONL 원본을 기록한다.

- Meta 앱 범위 사용자 ID
- Meta 인증 상태와 최초 방문/재방문 상태
- 연령대 값 또는 `Unknown` 상태
- 세션 ID, 시작 시각, 종료 시각, 종료 메모
- 씬 전환 및 `PPEVoiceFlowDirector`의 모드·시나리오·단계
- 단계 진입 시각과 단계 간 소요시간 계산에 필요한 이벤트
- 음원명, 음원 전체 길이, 재생 시작·종료 시각, 실제 재생 경과시간
- 음원 종료 상태: `completed`, `stopped`, `replaced`
- PPE enum 타입과 좌·우 구분
- PPE 검사 시작·종료, 상태(`Clean`/`Contaminated`)
- PPE 선택 행동과 결과(`UseApproved`, 오염 PPE 거부 등)
- 시나리오별 필수 PPE 목록
- 시점별 필수 PPE 완료 여부와 누락 PPE 목록
- Unity의 기존 PPE 로그 원문

실제 테스트에서 Meta 사용자 ID, 모드, 시나리오, 단계, 음원 길이·재생시간, PPE 결과, 누락 목록이 같은 `sessionId`로 연결되는 것을 확인했다.

### 17.3 대시보드에서 계산 가능한 지표

원본 이벤트에서 다음 지표를 계산할 수 있다.

- 사용자별 세션 수와 시나리오 수행 횟수
- 교육·훈련·테스트 모드별 수행 결과
- 시나리오별 완료율
- 완료 전 종료 세션 수와 중도 이탈률
- 마지막으로 도달한 단계
- 단계별 소요시간
- 음원 전체 길이 대비 실제 청취시간
- 음원 완료·중단·교체 비율
- PPE별 검사시간
- PPE별 선택 승인·거부 결과
- 오염 PPE 선택 실패
- 시나리오별 필수 PPE 누락률
- 정상 기록과 문제 기록의 원본 이벤트 상세

중도 이탈률은 다음 정의를 사용한다.

```text
중도 이탈률 = 완료 전 종료 세션 수 / 시작 세션 수 × 100
```

현재 `application_quitting`은 확인할 수 있지만 전원 종료, 백그라운드 전환, 충돌을 완전히 구분하지는 않는다. 해당 원인을 확정할 수 없을 때는 `종료 원인 미확인`으로 표시한다.

### 17.4 사용성 측정 기준

현재 계측으로 행동 기반 사용성을 측정할 수 있다.

- 단계별 체류시간
- PPE 검사에 머문 시간
- PPE 선택 실패와 재검사
- 필수 PPE 누락
- 음성 안내 중단·스킵
- 시나리오 완료 또는 완료 전 종료

다만 `그랩이 어려웠다`는 현재의 선택·검사 이벤트만으로 판단하지 않는다. 사용자가 그랩 버튼을 반복해서 눌렀지만 대상이 잡히지 않은 경우는 별도 입력 이벤트가 필요하다.

### 17.5 추가해야 하는 그랩 입력 데이터

PPE 마커 문제와 사용성 문제를 구분하기 위해 다음 이벤트를 추가한다.

- PPE 단계에서 발생한 실제 그랩 입력 시작
- 대상 PPE가 없는 상태의 입력
- PPE 마커를 가리켰지만 Select가 성립하지 않은 입력
- 실제 `selectEntered` 성공
- `selectExited` 해제
- PPE별 입력 횟수, 성공 횟수, 실패 횟수
- 첫 입력부터 그랩 성공까지의 시간
- 좌·우 컨트롤러 구분

음성 스킵용 트리거는 그랩 입력에 포함하지 않는다. 음성 스킵은 별도 이벤트로 기록한다.

```text
그랩 사용성 데이터
= PPE 단계의 그랩 입력
  - 음성 스킵 트리거 입력
  - UI 카드 입력
  - 텔레포트 입력
```

그랩 데이터가 추가되기 전에는 `반복 신호`, `그랩 실패 횟수`, `막힘 정도`를 대시보드에 표시하지 않는다.

### 17.6 표시하면 안 되는 임의 지표

다음 값은 원본 이벤트와 계산 규칙이 확보되기 전까지 목업 숫자로 표시하지 않는다.

- 도달 기록 수

- 어느 단계에서 더 막혔는가
- 전원종료 추정
- 문제신호 건수
- 그랩 실패 횟수

각 지표는 대시보드에서 값·산식·원본 이벤트·상세 이동 경로를 함께 제공해야 한다.

### 17.7 현재 검증 결과와 남은 검증

2026-08-26 실제 실행에서 다음을 확인했다.

정적 계측 파일이 존재하거나 JSONL이 생성된 것만으로 Quest 입력과 대시보드 연동이 완료되었다고 판정하지 않는다. Unity 재컴파일 후 실제 실행 기록과 원본 이벤트를 확인해야 한다.

### 17.8 종료 경로 사실 정정

종료 원인을 사용자가 별도 UI에서 선택한다고 가정하지 않는다. 현재 프로젝트에서 확인된 종료 경로는 기존 동작을 기준으로 구분해 계측해야 한다.

- `PPEExitTeleportMarkerRelay`의 `RequestExitReturn()` 및 `PPEFinaleController.ReturnAfterMidExitVoice()` 경로: `EXIT Point`를 통한 **중도 중단**
- 시나리오 카드 오른쪽의 기존 종료 버튼: 앱 종료 요청 경로. 실제 버튼 이벤트와 `Application.Quit()` 호출을 연결해 기록해야 함
- `PPETrainingTelemetryCapture.OnApplicationQuitting()`의 `session_ended / application_quitting`: 앱 종료 시점 기록일 뿐, 중도 EXIT·종료 버튼·전원 종료·충돌 원인을 그 자체로 구분하지 않음

따라서 대시보드의 이탈 원인은 사용자의 추가 응답으로 만들지 않고, 기존 EXIT Point·종료 버튼·앱 생명주기 이벤트와 종료 직전의 `sessionId`, 모드, 시나리오, 단계, PPE 상태를 연결해 표시한다. 실제 종료 경로 이벤트가 추가로 기록되기 전에는 세부 원인을 확정하지 않는다.

### 17.9 보고자료 사실성 하네스

`PPETrainingDataContractHarness`에 현재 locomotion 씬의 종료 경로 정적 검증을 추가한다. 하네스는 다음을 확인한다.

- 씬에 단일 `PPEExitTeleportMarkerRelay`가 있고 작성된 `PPEFinaleController`에 연결되어 있는지
- locomotion 씬의 EXIT Point가 walk-enter 방식으로 Player와 EnterVolume을 참조하는지
- EXIT relay가 `RequestExitReturn()`을 호출하고, finale가 `ReturnAfterMidExitVoice()`와 `NotifyMidExitArrived()`를 사용하는지
- 씬의 기존 `QuitApplicationButton`이 Unity UI Button과 연결되고 `Application.Quit()` 경로를 갖는지
- 현재 텔레메트리가 `session_ended / application_quitting`을 기록하는지

이 하네스 PASS는 종료 경로의 **정적 연결**만 증명한다. EXIT Point와 종료 버튼이 서로 다른 원본 이벤트로 JSONL에 기록되었다는 뜻은 아니다. 해당 이벤트가 실제 실행 로그에 추가·검증되기 전에는 대시보드에서 세부 이탈 원인을 확정값으로 표시하지 않는다.

```text
좌·우 XRController GripButton
→ XRI Left/Right Interaction의 Select
→ Left/Right_NearFarInteractor
→ PPE XR Item Marker_small Collider
→ XRGrabInteractable hover
→ selectEntered / selectExited
```

음성 스킵은 Trigger 기반 별도 입력이므로 그랩 계측에 포함하지 않는다. 계측은 `PpeArea` 상태에서 실제 Select action의 active control path에 `grip`이 있는 경우만 시작한다.

추가한 원본 이벤트는 다음과 같다.

- `ppe_grab_attempted`: 실제 Grip 입력 시점, 좌·우 손, control path, hover 중인 PPE 수와 목록
- `ppe_grab_attempt_resolved`: 같은 attemptId의 결과와 입력 후 경과시간
- `ppe_grab_release_input`: Toggle 선택 중 다시 Grip을 누른 해제 요청
- `ppe_grab_released`: 실제 `selectExited`
- `ppe_grab_selected_without_attempt`: controller Grip 입력을 관찰하지 못했지만 `selectEntered`가 발생한 계측 불일치 신호

결과값은 관찰 가능한 사실로 제한한다.

- `selected`: Grip 입력 뒤 실제 `selectEntered` 발생
- `no_ppe_hover`: Grip 입력 시 PPE hover가 없고 0.5초 안에 선택되지 않음
- `hover_without_select`: PPE hover는 있었지만 0.5초 안에 선택되지 않음
- `repeated_before_select`: 이전 시도가 해결되기 전에 같은 손 Grip이 다시 입력됨
- `session_ended_before_resolution`: 결과 판정 전에 세션이 종료됨

각 기록은 기존 `sessionId`, Meta 앱 범위 사용자 ID, 모드, 시나리오, flowState, PPE itemType과 함께 저장된다. 대시보드의 그랩 실패 횟수와 반복 신호는 `ppe_grab_attempt_resolved`의 결과를 집계해 계산하며, 원본 이벤트가 없는 이전 세션에는 계산하지 않는다.

정적 하네스는 좌우 NearFarInteractor, 좌우 XRI Select의 `{GripButton}` 바인딩, `PpeArea` 제한, grip control 필터와 이벤트 이름을 검사한다. Unity Play/OpenXR 실측 세션 `078c1666ac8c4defa3794799b28f5bf2`에서는 Right Grip 4회 중 PPE hover 상태의 `selected` 2회와 PPE 비-hover 상태의 `no_ppe_hover` 2회가 기록됐다. 입력 경로는 `/OculusTouchControllerOpenXR1/grippressed`였고 각 시도는 `attemptId`로 시작·결과가 연결됐다. Quest 독립 실행 빌드의 동일 결과는 아직 별도 검증이 필요하다.

### 17.12 실제 JSONL 조회 대시보드 전환

#### 적용한 변경

`server/public/dashboard/index.html`의 기존 모의 사용자·모의 세션·임의 지표를 제거하고, Unity가 실제 저장한 세션 JSONL만 조회하는 화면으로 교체했다. 로컬 서버에는 다음 읽기 전용 API를 추가했다.

- `GET /api/local-telemetry/sessions`: 실제 세션 파일의 요약 목록
- `GET /api/local-telemetry/sessions/:sessionId`: 같은 세션의 요약, 유효 이벤트, JSON 파싱 오류 원본

대시보드는 `Meta 앱 범위 사용자 ID → sessionId → 모드·시나리오 → 단계 → PPE·음성·그랩 이벤트` 관계를 유지한다. 전체 개요, 사용자별 기록, 시나리오·PPE, 사용성·그랩에서 표시한 행이나 검토 신호를 누르면 해당 원본 이벤트로 이동한다. JSON 파싱 오류는 파일명, 행 번호, 파서 메시지, 깨진 원본 행을 별도 근거 화면에 표시한다.

#### 근본 원인

기존 화면은 계산 기준과 원본 이벤트가 없는 목업 수치를 독립적으로 표시해 같은 사용자의 수행 변화나 경고의 발생 근거를 역추적할 수 없었다. 특히 완료, 중도 종료, 필수 PPE, 그랩 실패를 서로 다른 데이터처럼 표현해 실제 Unity 수집 가능 여부와 대시보드 계산 가능 여부가 섞였다.

#### 영향 범위

- 사용자별: 식별된 Meta 앱 범위 ID와 미식별 세션을 분리하고 각 세션 상세로 이동
- 시나리오별: 실제 `workPlan`과 `missingRequiredPpe`에서 관찰된 필수 PPE 전체 목록 표시
- PPE별: 검사 시작, 선택 결과, 오염 거부, 검사시간, 그랩 계측 여부를 같은 `sessionId`에서 집계
- 단계별: 연속 `flow_state_changed.timestampUtc` 차이로 체류시간 계산
- 종료: `application_quitting`을 종료 시점으로만 표시하고 종료 원인으로 확정하지 않음
- 데이터 품질: 유효 JSON 이벤트와 파싱 오류를 분리하고 오류 원문까지 조회

#### 완료한 검증

2026-08-26 현재 로컬 저장소에서 실제 8세션, 유효 이벤트 828건, JSON 파싱 오류 0건을 API와 화면에서 확인했다. 식별된 Meta 사용자는 1명이고 미식별 세션은 2건이다. `flowState=Completed`가 관찰된 세션은 1건이며, 나머지 7건은 `완료 전 종료`로만 표시한다.

- 최근 세션 행에서 `689741cb2fb9488e9489bc5234543b36` 상세로 이동 확인
- 같은 세션의 단계별 시간, PPE별 선택 결과, 음성 길이·실제 재생시간 표시 확인
- 원본 이벤트 828건과 Meta 식별 이벤트 8건 필터 확인
- 그랩 계측 전 7세션은 Grab 값을 `0`이 아닌 `미계측`으로 표시 확인
- 신규 세션 `078c1666ac8c4defa3794799b28f5bf2`에서 실제 Right Grip 시도 4회, `selected` 2회, `no_ppe_hover` 2회 확인
- 같은 신규 세션의 `ppe_grab_*` 원본 11건과 `attemptId`, OpenXR 입력 경로, hover PPE, 처리시간을 대시보드에서 확인
- JSON 파싱 오류 필터가 파일·행·메시지·원본 행 표를 제공하는지 테스트 픽스처로 확인
- 데스크톱 1440×1000 및 모바일 390×844 렌더링 확인
- 서버 관련 자동 테스트 12건 통과, 대시보드 JavaScript 구문 검사 통과, 브라우저 Console/Page 오류 없음

#### 아직 필요한 수동 검증

- Quest 독립 실행 빌드에서도 동일한 그랩 이벤트와 Meta ID가 기록되는지 확인
- EXIT Point와 카드 오른쪽 종료 버튼을 서로 구분하는 종료 경로 이벤트 추가 후 실측
- 운영 DB, 인증, Quest 독립 실행의 PC LAN 주소·Android HTTP 설정은 별도 배포 단계에서 검증

현재 대시보드는 운영 DB가 아니라 개발 PC의 Unity JSONL 디렉터리를 읽는 로컬 검증용이다. 이 범위를 넘어 Meta Horizon 사용자의 원격 기록이 자동 수집된다고 해석하지 않는다.

### 17.13 Unity 로그·런타임 상태 추가 데이터 점검

#### 대시보드 로딩 실패 원인과 수정

대시보드 HTML을 폴더에서 직접 열면 주소가 `file://.../server/public/dashboard/index.html`이 된다. 이 경우 상대 경로 `/api/local-telemetry`에는 HTTP 서버가 없으므로 `데이터를 불러오지 못했습니다`가 표시된다. 정상 접속 주소는 `http://localhost:3000/dashboard/`이다.

동일 실수를 반복해도 복구되도록 `file:` 프로토콜에서 열렸을 때 `http://127.0.0.1:3000/dashboard/`로 자동 이동하는 처리를 추가했다. 이 자동 이동은 로컬 Express 서버가 실행 중이라는 전제이며 서버를 자동 실행한다는 뜻은 아니다.

#### 현재 JSONL에 이미 구조화된 원본

2026-08-26의 실제 8세션·828개 유효 이벤트에는 다음 16개 이벤트 유형이 있다.

- 세션·씬: `session_started`, `scene_loaded`, `session_ended`
- 사용자: `meta_identity_state_changed`
- 과정: `flow_state_changed`, `required_ppe_status_changed`
- PPE: `ppe_inspection_started`, `ppe_inspection_stopped`, `ppe_condition_changed`, `ppe_choice_resolved`
- 그랩: `ppe_grab_attempted`, `ppe_grab_attempt_resolved`, `ppe_grab_release_input`, `ppe_grab_released`
- 음성: `voice_playback_started`, `voice_playback_ended`
- 보조 로그: `unity_ppe_log`

이 원본으로 사용자 ID, 연령 범주 상태, 모드, 시나리오, 단계 체류시간, 씬 이동 순서, 필수 PPE 누락 목록 변화, PPE 검사시간, 청결·오염 상태, 사용 승인·거부, 음성 길이·실제 재생시간, Grip 손·입력 경로·hover 대상·성공/실패·처리시간을 계산할 수 있다.

#### 이미 존재하지만 대시보드에서 아직 집계하지 않은 실제 데이터

- `scene_loaded` 36건: 시작 씬부터 PPE 룸까지의 씬 이동 순서와 구간별 소요시간
- `metaProbeState`, `metaWelcomeState`: Meta 진단 단계와 `FirstVisit` 상태
- `required_ppe_status_changed` 56건: 필수 PPE 누락 개수의 시간별 감소 과정
- Grab release 이벤트: Grip 해제 요청과 실제 `selectExited` 확인
- `server/data/local-training-registrations.jsonl`: 교사 왕복 시험 1건과 실제 세션 2건의 `serverReceivedAt`. Unity 세션 JSONL과 `sessionId`로 결합 가능
- `[PPE Equip]` 로그: 방호복 body proximity 착용 완료 사실. 현재는 `unity_ppe_log` 문자열이므로 교육 지표로 집계하려면 구조화 이벤트로 승격해야 함
- `[PPE METRICS]` 로그: Editor/Quest Link 기준 Draw Calls·Triangles·Vertices 1회 측정. Android Quest 성능 결과가 아니므로 사용자 수행 지표와 분리해야 함
- Unity OpenXR 진단 로그: Oculus Quest 2, Oculus Runtime 1.206.0, Single Pass Instanced, 권장 양안 해상도. Editor 진단 정보이며 운영 사용자 세션 원본은 아님

#### 코드 상태는 있으나 JSONL 이벤트가 없는 항목

다음 값은 현재 런타임 코드가 이미 알고 있지만 텔레메트리로 내보내지 않는다. 따라서 지금 대시보드에 수치로 표시하면 안 된다.

- `PPEHazmatEquipController.IsEquipped`, `PPEHelmetEquipController.IsEquipped`, `PPEEquipmentVisualController.IsItemUsed`: 실제 착용·착용 애니메이션 완료
- `PPETabletChecklistController.DocumentCompleted`: 태블릿 체크리스트·서명 완료
- `NotifyTeleportStarted`, `NotifyTeleportCanceled`, `NotifyTeleportArrived`: 텔레포트 시도·취소·도착
- `PPEExitTeleportMarkerRelay`와 `QuitApplicationButton`: EXIT Point 중도 중단과 앱 종료 버튼의 경로 구분
- `NotifyQuizCompleted(correctAnswerCount)`와 `m_ModeSessionElapsed`: 퀴즈 정답 수와 모드 수행시간
- 컨트롤러 교육의 기대 입력·실제 입력·정답/오답 결과
- Trigger 음성 스킵 입력: 현재 `voice_playback_ended`의 `stopped` 또는 `replaced`만으로는 사용자 스킵인지 상태 전환인지 구분할 수 없음
- PPE hover 시작·종료: 현재는 Grip 입력 순간의 hover 상태만 있어 `hover 시작 → Grip → Select` 전체 지연을 계산할 수 없음

#### 추가 계측 우선순위

1. `appVersion`, Android version code, 실행 플랫폼, 장치·XR runtime을 `session_started`에 기록한다. 현재 프로젝트 값 `bundleVersion=0.1.0`, `AndroidBundleVersionCode=1`은 세션 JSONL에 없다.
2. 전체 14종 PPE 카탈로그와 시나리오별 필수 목록을 세션 스냅숏으로 기록한다. 현재 필수 목록은 `missingRequiredPpe`에서 관찰한 값이라 이미 착용된 장비나 미진입 세션에서는 완전한 원본이 아니다.
3. `ppe_equipped`를 선택 승인과 분리해 실제 착용 완료 시점에 기록한다.
4. EXIT Point, 종료 버튼, 앱 생명주기를 각각 다른 종료 경로 이벤트로 기록한다.
5. 태블릿 시작·완료, 퀴즈 문항별 선택·정답·최종 점수, 모드 수행시간을 기록한다.
6. 텔레포트 시작·취소·도착과 Trigger 음성 스킵을 구조화한다.
7. PPE hover enter/exit를 추가해 hover 후 Grip 지연과 Grip 후 Select 지연을 분리한다.
8. FPS·frame time·XR 성능은 교육 결과와 분리된 진단 데이터로 저장한다.

우선순위 1~7은 기존 상태 소유자의 이벤트나 속성에서 직접 얻을 수 있다. 다만 이벤트를 추가한 뒤 실제 Unity Play/Quest JSONL 검증을 거치기 전에는 대시보드에서 측정 완료로 표시하지 않는다.

2026-08-26 작업 결과와 담당 선생님 피드백에 따른 데이터 활용 중심 후속조치는 [PPE 훈련 데이터·대시보드 후속 회의록](./2026-08-26_PPE_Training_Data_Dashboard_Followup.md)에 정리했다.
