# 2026-09-06 기업연계 VR 프로젝트 개인 발표 포지셔닝 회의록

- 일자: 2026-09-06
- 범위: 기업연계 VR 프로젝트 최종 발표에서 개인 기여와 시연 포지션을 정리한다.
- 대상: VR 회사 관계자 및 기업 대표가 참석할 수 있는 최종 발표·시연
- 관련 기준: 클라이언트 저장소의 현재 구현과 별개로, 개인 발표 전략을 정리하는 문서다.

## 1. 상황과 문제 정의

이번 발표에서는 여러 팀이 거의 같은 제작 도구를 사용했고, 모든 팀이 구현 결과물을 완성했다. 다른 팀에는 게임 제작 경험, 3D 디자인 경험, 깊은 개발 경험 등 특정 분야의 강점이 있다. 본 프로젝트의 개인 작업은 1인 팀으로 진행했으며, 상세 기획서를 먼저 작성하고 기획·자산 확보·구현·정리까지 전체 흐름을 혼자 연결했다.

따라서 최종 화면의 화려함이나 특정 전문 기술만 단순 비교하면 개인 기여가 잘 드러나지 않을 수 있다. 특히 다른 팀도 비슷한 방식으로 기획을 실행하고 결과물을 발표할 수 있으므로, 단순히 `기획을 먼저 했다`, `혼자 했다`, `AI를 사용했다`만으로 차별화하지 않는다.

이번 발표의 목표는 다른 팀보다 모든 분야를 잘했다고 주장하는 것이 아니다. 제한된 자원 안에서 교육 목적의 VR 경험을 하나의 완결된 흐름으로 설계하고, 그 판단을 설명할 수 있는 사람이라는 점을 보여주는 것이다.

## 2. 이번 발표가 대응하는 메시지

### 핵심 메시지

> 전문 모델러나 대규모 개발팀으로서 경쟁한 것이 아니라, AI와 기존 자산·Unity·서버를 조합해 교육 목적의 VR 경험을 처음부터 끝까지 연결했다.

### 기업연계 프로젝트의 의미

이번 발표는 VR이 없는 기업에 VR 라인 구축을 설득하는 영업 발표가 아니다. 기업이 제시한 과제를 VR 체험 콘텐츠로 해석하고 구현한 결과를 보여주며, 실제 프로젝트에서 요구되는 문제 정의·우선순위 판단·협업·설명 능력을 검토받는 자리로 본다.

따라서 `왜 VR 교육이 필요한가` 또는 `왜 기업이 VR 라인을 새로 만들어야 하는가`를 발표의 중심으로 삼지 않는다. 대신 다음을 중심으로 설명한다.

- 어떤 교육 문제를 체험 과제로 해석했는가
- 사용자가 무엇을 어떤 순서로 해야 하는가
- 왜 해당 기능을 넣고 다른 기능은 제외했는가
- 사용자의 실수와 완료를 어떻게 구분하는가
- 교육 결과와 운영 데이터를 어떻게 연결할 수 있는가
- 현재 결과물의 한계와 다음 확장 지점은 무엇인가

## 3. 개인 포지션

개인 포지션은 `전문 3D 모델러`나 `수석 개발자`로 설정하지 않는다. 다음과 같이 정의한다.

> 아이디어를 실행 가능한 VR 프로젝트 구조로 구체화하고, 제한된 시간과 자원 안에서 여러 도구를 연결해 하나의 체험으로 완성한 사람

실제로 설명할 수 있는 책임 범위는 다음과 같다.

- 초기 문제 정의와 상세 사용자 흐름
- 기능 우선순위와 체험 순서
- 교육 목적과 상호작용의 연결
- AI 및 기존 에셋을 활용한 시각 자산 확보
- Unity 구현 범위 조정
- 클라이언트·서버 흐름을 고려한 결과 기록 방향
- 시연 가능한 결과물로 정리하고 설명하는 작업

이 포지션은 다른 팀보다 모든 기술 분야가 우수하다는 주장이 아니다. 전문 영역이 나뉜 팀과 달리, 1인 작업에서 전체 연결부와 우선순위를 책임졌다는 점을 보여주는 전략이다.

## 4. 발표에서 피해야 할 비교와 표현

다음 표현은 확인하기 어렵거나 다른 팀을 공격하는 인상으로 이어질 수 있으므로 사용하지 않는다.

- `다른 팀이 제 기획을 따라 했다.`
- `제가 원조라서 다른 팀보다 우수하다.`
- `AI가 대부분 만들어 줬다.`
- `모델링과 개발은 못하지만 혼자 했다.`
- `다른 팀은 에셋을 가져왔을 뿐이다.`

대신 개인 기여를 긍정적이고 검증 가능한 문장으로 설명한다.

> 초기 단계에서 교육 목표를 사용자 흐름과 기능 요구사항으로 구체화하고, 이를 상세 문서와 구현 기준으로 정리했습니다.

> 전문 자산 제작만을 목표로 하기보다 제한된 시간 안에 필요한 시각 자산을 확보하고, 사용자가 체험하는 흐름과 결과 확인까지 연결하는 데 집중했습니다.

> 결과 화면만 보여주는 것이 아니라 왜 이 순서와 상호작용을 선택했는지, 실제 기업 교육에 적용할 때 어떤 부분을 확장해야 하는지 설명할 수 있도록 구성했습니다.

## 5. 권장 발표 흐름

1. **과제 해석**
   - 기업연계 과제를 어떤 교육 상황으로 해석했는지 설명한다.
2. **사용자 흐름**
   - 시작, 안내, PPE 선택·착용, 위험 대응, 결과 확인의 흐름을 짧게 보여준다.
3. **핵심 판단**
   - 기능을 많이 넣기보다 사용자가 무엇을 배우고 무엇을 판단해야 하는지에 따라 우선순위를 정했다고 설명한다.
4. **직접 시연**
   - 한 가지 대표 시나리오를 끝까지 보여준다. 기능을 나열하지 않는다.
5. **운영 관점**
   - 결과가 어떤 이벤트와 세션 단위로 기록될 수 있는지 설명한다. 실제 서버 조회·저장 여부는 확인된 범위만 말한다.
6. **한계와 확장**
   - 모델 품질, 콘텐츠 수, 실기 검증 등 아직 남은 부분을 숨기지 않고 다음 개발 범위로 제시한다.

## 6. 1분 개인 소개 예시

> 저는 전문 모델러나 대규모 개발팀의 역할을 맡은 것이 아니라, 1인 작업으로 프로젝트 전체 연결을 담당했습니다. 먼저 교육 목표와 사용자 흐름을 상세 기획서로 구체화한 뒤, AI와 기존 자산을 활용해 필요한 시각 요소를 확보하고 Unity에서 체험 흐름으로 연결했습니다. 제가 집중한 부분은 화면을 많이 만드는 것이 아니라 사용자가 무엇을 보고, 선택하고, 실수하고, 완료하는지를 하나의 과정으로 설계하는 것이었습니다. 그래서 이 결과물을 실제 기업 교육에 적용할 때 필요한 평가 기준과 데이터 연결 지점까지 설명할 수 있도록 준비했습니다.

## 7. 발표 전 준비할 개인 근거

다음 자료는 다른 팀과의 우열을 주장하는 자료가 아니라, 개인 기여와 판단 과정을 확인하기 위한 근거로 보관한다.

- 상세 기획서의 최초 작성본과 버전 기록
- 사용자 흐름·상태 전이·기능 우선순위 표
- 초기 기획에서 최종 구현으로 바뀐 항목과 변경 이유
- AI 또는 기존 에셋을 사용한 범위와 직접 조정한 범위
- 구현 중 발생한 문제와 해결 과정
- 클라이언트·서버 데이터 연결을 설명할 수 있는 파일·로그·테스트 근거
- 발표 시 직접 담당할 시연 단계와 예상 질문 답변

현재 자료만으로 확인되지 않는 채용 가능성, 실제 기업 도입 효과, 서버 운영 규모, Quest 실기 성공 여부는 확정적으로 말하지 않는다. 해당 내용은 코드에 존재함, 씬에 연결됨, 실행 로그로 수집됨, 서버·대시보드에서 조회됨을 각각 분리해 확인한 뒤 발표 문구에 반영한다.

## 8. 남은 실행 항목

- 개인 기획서의 작성 시점과 버전을 별도 폴더 또는 제출 자료에서 확인한다.
- 대표 시연용 핵심 흐름을 3~5분 안에 끝나는 단일 시나리오로 정한다.
- 시연 중 직접 설명할 상태 전이와 데이터 기록 지점을 표시한다.
- 실제 서버 저장·조회 결과를 보여줄 경우 클라이언트와 서버의 기준 브랜치·커밋 SHA 및 실행 로그를 대조한다.
- 발표 자료에서는 `완료`, `정적 확인`, `Unity Editor 확인`, `Play Mode 확인`, `Quest/OpenXR 확인`, `미검증`을 섞지 않는다.
- 발표 전 개인 기여 근거를 강사 또는 평가자에게 제출할지 여부를 결정한다.

## 9. 결론

최종 결과물만 보면 3D·개발·게임 제작 경험이 강한 팀과의 비교에서 불리할 수 있다. 그러나 이 프로젝트의 개인 강점을 모든 분야의 전문성으로 포장하지 않는다. 상세 기획을 구현 가능한 구조로 바꾸고, 제한된 자원과 AI·기존 자산을 활용해 클라이언트·서버·시연 흐름을 하나로 연결한 실행력과 판단력을 핵심 메시지로 삼는다.

발표의 성공 기준은 `가장 화려한 결과물`이 아니라 `이 사람에게 실제 과제를 맡겼을 때 문제를 구조화하고 끝까지 연결할 수 있겠다는 신뢰`를 주는 것이다.

### 기획 방향 전환의 배경

초기 방향은 `PPE 착용교육 + 다른 안전 시나리오`를 함께 구성하는 것이었다. 당시에는 교육·훈련·테스트 3모드를 구현하고 싶었지만, 개발 경험과 3D 제작 경험이 충분하지 않아 여러 시나리오와 모드를 동시에 완성할 수 있을지는 불확실했다.

사전기획 발표 이후 `교육·훈련·테스트 버전으로 구현해 보는 것이 어떻겠는가`라는 피드백을 받았고, 방향을 `PPE 하나라도 교육·훈련·테스트로 제대로 완성하는 것`으로 전환했다. 이는 처음 기획을 실패한 것이 아니라, 피드백과 제작 리스크를 반영해 검증 가능한 하나의 제품 단위로 범위를 재설정한 결정이다.

이 전환은 현재 프로젝트 구조와 직접 연결된다.

- 공통 PPE 수행 코어를 유지한다.
- 모드별로 안내·오류 피드백·힌트·결과 공개 정책을 분리한다.
- `PPEVoiceFlowDirector`가 진행 상태와 작업계획을 관리한다.
- `PPEQuizController`가 모드·작업계획별 문제 풀과 결과를 관리한다.
- `PPETrainingTelemetryCapture`가 모드 실행·퀴즈·완료를 세션 단위로 기록한다.
- 서버는 해당 실행을 세션·이벤트·완료 계약으로 수신하고 조회한다.

따라서 발표에서 이 변경은 다음과 같이 설명한다.

> 처음부터 많은 시나리오를 넓게 만드는 대신, 피드백을 반영해 PPE라는 하나의 핵심 교육을 교육·훈련·테스트로 깊게 구현했습니다. 결과적으로 범위는 좁아졌지만, 사용자의 행동·모드별 지원·완료 결과·서버 기록까지 하나의 흐름으로 검증할 수 있는 구조를 만들었습니다.

### 논리가 실제 구현으로 연결된 부분

1. **퍼소나의 문제 → 상태·입력 설계**
   - 퍼소나 김도윤은 안전수칙을 알고 있지만 실제 절차 순서와 판단에 자신이 없는 현장 1년차 작업자로 설정되어 있다.
   - 현재 클라이언트는 `PPEVoiceFlowDirector`가 흐름 상태를 소유하고, `ScenarioDetailModal`의 `Education`, `Training`, `Test` 모드로 안내 수준을 나눈다.
   - PPE 선택·점검·사용/폐기 판정·착용·최종 확인·퀴즈가 선행조건을 통해 연결되어 있어, “알고 있는 지식”을 “순서가 있는 행동”으로 바꾸려는 기획 논리가 구현에 반영되어 있다.

2. **교육 아이덴티티 → 상호작용 규칙**
   - 제품은 단순 감상형 VR이 아니라 `직접 판단하고 수행한 뒤 결과를 확인하는 절차형 안전교육`으로 정의되어 있다.
   - 현재 PPE는 손으로 잡고, 점검하고, 공용 Action Panel에서 사용 또는 폐기를 선택한다. 교육모드는 오류 이유와 재안내를 제공하고, 훈련·테스트는 지원 수준과 결과 노출을 다르게 적용한다.
   - 이 구조는 상세기획서의 “교육·훈련·테스트는 같은 PPE 수행 코어를 공유하고 지원 정책만 다르게 한다”는 설계와 일치한다.

3. **제품 가치 → 데이터 구조**
   - 최종 PT의 `행동을 데이터로 남긴다`는 메시지는 현재 클라이언트와 서버의 공통 계약으로 연결되어 있다.
   - 클라이언트는 모드 세션 시작, 퀴즈 답변, 모드 세션 완료를 `modeSessionId`로 연결하고, 모드·작업계획·퀴즈 정오답·PPE 오답 횟수·소요시간을 기록한다.
   - 서버는 세션 생성, 이벤트 배치 저장, 세션 완료, 세션·참여자 조회 API를 제공하며, `Education`, `Training`, `Test` 측정 이벤트와 필요한 필드를 검증한다.
   - 따라서 `행동 → 이벤트 → 세션 → 조회`라는 제품 논리는 코드와 API 수준에서 확인된다.

4. **개인 기획 역량 → 현재 결과물의 구조**
   - 상세기획서가 정의한 상태·모드·QA 관점이 실제 코드의 상태 소유자, 모드별 정책, 결과 화면, 텔레메트리 함수로 나뉘어 있다.
   - 이는 단순히 3D 공간을 만든 결과보다, 교육 목적을 실행 규칙과 검증 가능한 데이터로 번역한 결과로 설명할 수 있다.

## 11. 현재 구현 기준으로 대체해야 하는 범위

### 문서와 프로젝트 로직의 기준 우선순위

상세기획서와 사전기획서는 개발 전 의도와 확장 방향을 설명하는 기준 문서다. 아직 문서가 현재 구현까지 현행화되지 않은 항목은 발표나 검토에서 문서의 과거 표현을 현재 기능으로 확정하지 않고, 프로젝트 폴더의 최신 코드·씬·빌드 설정·서버 계약을 현재 기준으로 사용한다.

현재 코드의 `PpeWorkPlan`은 `ConfinedSpace`와 `LeakResponse` 두 작업계획을 제공하고, 활성 빌드 씬은 `Assets/Scenes/4_PPE_Room.unity`까지다. `5_MixerRoom`과 `6_InsideMixer`는 현재 빌드에서 비활성이다. 이는 기획이 잘못되었다는 뜻이 아니라, 개발 전 계획보다 현재 프로젝트 로직을 우선해 발표해야 한다는 뜻이다.

따라서 발표에서는 다음처럼 말해야 한다.

> 현재 시연·검증 범위는 PPE 수행을 중심으로 두 작업계획과 세 학습모드의 조합을 구현한 프로토타입입니다. 밀폐공간 전체 절차와 사고 체험은 후속 확장 범위로 분리합니다.

현재 발표 PT의 `작업계획 2종 × 학습모드 3종` 표현은 프로젝트 폴더의 현재 로직을 반영한다. 사전기획서의 `세 시나리오 모두 5문항` 또는 사고 체험 설명은 개발 전 계획 또는 후속 방향으로 읽고, 현재 구현 완료 사실을 설명할 때는 코드·씬·서버 계약으로 대체한다.

### PPE 개수 표현

상세기획서는 PPE를 7종의 교육 범주로 설명하지만, 현재 런타임은 좌·우 장갑·장화를 개별 슬롯으로 분리하고 내·외부 장갑을 구분해 작업계획별 필수 배열을 관리한다. 현재 코드의 필수 배열은 작업계획별로 10개 항목까지 포함한다.

따라서 `PPE 7종`은 기획상의 범주 수로, 실제 구현에서는 `좌·우 및 내·외부 착용 슬롯을 포함한 필수 항목`으로 설명해야 한다. 숫자를 그대로 비교하면 기획서와 코드가 불일치하는 것처럼 보일 수 있다.

## 12. 서버 연계에 대한 사실성 경계

현재 서버 코드와 문서에서 확인되는 것은 다음 범위다.

- `POST /api/training-telemetry/sessions`
- `POST /api/training-telemetry/sessions/:sessionId/events`
- `POST /api/training-telemetry/sessions/:sessionId/complete`
- 세션·참여자 조회 API
- Bearer 인증 미들웨어와 이벤트 스키마 검증
- MySQL 저장소와 개발용 원본 조회 화면

이 근거만으로 `기업 운영 대시보드가 이미 완성되어 공식 직원 평가를 제공한다`고 말하지 않는다. 공식 평가에는 사번·소속 연결, 합격 기준, 재응시 정책, 미수집·중도 종료 예외 처리가 추가로 필요하다. 현재 PT의 서버 설명은 `운영 데이터 기반과 조회 계약이 구현되어 있다`로 표현하고, Quest에서 실제 실행한 세션이 서버와 대시보드까지 종단간 조회되는지는 별도 검증 결과로만 확정한다.

## 13. 발표 논리의 최종 형태

발표에서 사용할 연결 구조는 다음과 같다.

`김도윤의 문제`
→ 안전수칙은 알지만 순서와 판단을 놓칠 수 있음
→ `교육 설계`
→ 직접 잡고 점검하고 판정하며, 모드별 지원 수준으로 반복 수행
→ `제품 구조`
→ PPE 상태·작업계획·모드·퀴즈·완료 조건을 하나의 실행 세션으로 관리
→ `서버 가치`
→ 행동 이벤트와 결과를 세션 단위로 저장·조회
→ `기업 확장`
→ 실제 작업계획·직원 식별·평가 정책·운영 대시보드로 확장

이 흐름에서 현재 구현 완료와 향후 제품화를 섞지 않는다. 현재는 `교육 경험과 계측 가능한 프로토타입`까지를 확정하고, 공식 기업 평가·전체 밀폐공간 시나리오·사고 체험·Quest 종단간 운영 검증은 후속 단계로 표시한다.

## 14. 검토 결론

기획의 핵심 논리는 프로젝트로 연결되어 있다. 가장 강한 연결은 퍼소나의 불안 요소를 상태 전이와 오류 복구로 바꾸고, 교육 결과를 서버가 읽을 수 있는 이벤트 계약으로 확장한 부분이다.

가장 중요한 원칙은 문서와 구현이 다를 때 현재 프로젝트 로직을 기준으로 삼는 것이다. 발표에서는 현재 활성 씬과 현재 코드가 보장하는 `2개 작업계획 × 3개 모드`를 기준으로 말하고, 상세기획서에 아직 반영되지 않은 변경은 `프로젝트 폴더 현행 로직 기준`으로 설명한다. 사고 체험·전체 밀폐공간·공식 평가처럼 현재 로직에서 확인되지 않는 표현만 `후속 확장` 또는 `미검증`으로 분리한다. 이렇게 하면 문서의 미현행화가 오히려 현재 구현을 정확히 읽고 설명하는 역량을 가리는 일이 없어진다.
